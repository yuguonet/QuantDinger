## 4. 逐条方案

### P0-1【最严重】`run_monitor_safe` 不存在 → 盘中状态机整条停摆

**现象**：`scheduler.py:363-364` `from app.market_cn.auto.monitor import run_monitor_safe`，而
`monitor.py` 只有 `run_monitor()`（:389）。Task `dragon_monitor`（60s）每次触发在 import 处抛
`ImportError`，被 `scheduler.py:770-773` 的 `except Exception` 吞成一条日志。
⇒ 开盘 gap 买入、盘中止损、预确认、收盘出场、15:01 确认、exit 平账、组对账**全部不执行**。

**为什么不偏离**：目标态 §4.4「盘中也是主干」、§4.2「实时=当日事件投影」；盘中停摆等于主干少一整个视图。

**修法（三步，按此序）**：

1. **先止血**：`monitor.py` 增一行显式别名 `run_monitor_safe = run_monitor`，并在 docstring 注明
   「这是调度器契约名，语义=run_monitor；**不要**在此加 try/except 吞异常」。
   —— 选择「补别名」而非「改 scheduler」，理由：调度器调用点是契约边界，别名让**契约名与实现名解耦**，
   未来若要加真正的安全包装（如单实例锁）有落点；改 scheduler 则要动 `app/market_cn/scheduler.py`
   （跨层），违反设计 §2.2 依赖方向的收敛方向。
2. **堵静默**：`scheduler.py:770-773` 的 `_worker` 异常处理，对 **ImportError/AttributeError** 这类
   「接线错误」**不得降级为日志**：至少 `logger.exception` + 计入一个 `scheduler_health` 计数
   （若已有健康字段则复用；无则**先不加字段**，改为启动期自检，见 3）。
3. **加静态防线**：新增 `tests/present/test_scheduler_imports.py`，用 AST 静态解析
   `scheduler.py` 内所有 `from app.market_cn.auto.X import Y`，断言 `Y` 在 `X` 的顶层定义中
   （**不 import，只解析**，零副作用、秒级）。这是唯一能防住「同名不存在」的自动化手段。

**验收**：① 导入面冒烟（设计 §9.1「目录搬迁」行）全过；② 新测试绿；
③ 手工 `python -c "from app.market_cn.auto.monitor import run_monitor_safe"` 成功；
④ `pytest` 全绿。

**风险**：极低。**但必须诚实说明**：别名只解决「函数找不到」，**不解决盘中逻辑本身的正确性**——
盘中链此前长期空转，历史上可能已积累被 stale 过期吃掉的脏状态（`watch_pending` 滞留）。
修复后**首个交易日必须人工盯盘**一次，确认不会出现「一夜之间补跑大量补单」。

### P0-2 生产切片无人推进 → Record 事实流在生产链上是断的

**现象（证据链）**：
- `config.json:9 "scan_writer": "scan_day"` ⇒ 行源走 `scan.py:508 WRITER` → `_rows_by_scan_day`（:573-577），
  判定引擎 = 门表 `core.runtime.evaluate.scan_day`；
- 切片唯一生产写入口 `present_daily.persist_days` **只被 `_rows_by_record`（scan.py:732）调用**
  ⇒ 在 scan_day 模式下**永不执行**；
- `monitor._progress_map`（:331-386）读同一 StateStore 切片 ⇒ `core/present/realtime.py:20` 明文
  「切片只由预处理推进」⇒ 切片缺失/stale ⇒ **四判定点恒回退旧 confirm/exit/entry_decision**（安全但空转），
  config 承诺的观察灯 `no_judgment==0 / confirm_prog_hit>0` **永不可能过线**；
- `startup._rebuild_worker`（:513）→ `rebuild.projection_ledger_refresh` → 切片无投影时返回
  `(None, {"error":"切片无投影"})`（rebuild.py:973-975）→ `_RebuildIncomplete` → **指纹不推进**（:527-537）
  ⇒ 每次重启重复「补扫 + 刷新失败」。
- `present_daily.enabled()`（`present_persist.enabled` 读取口）**生产零消费者**。

**为什么不偏离**：目标态 §4.2「事件流是唯一事实」+ §4.3「展示层消费事件流」。当前生产**没有人在推进事件流**，
四视图同源在生产侧不成立。

**修法（推荐路线 A，附路线 B 的取舍）**：

- **路线 A（推荐）**：`scan_writer` 切回 `"record"`，即让 `scan_days` 走 `_rows_by_record`
  （Record 驱动，与目标态 §4.1「主干=逐天复现」一致）。
  - 配套：**收敛双开关语义**——`present_persist.enabled` 与 `scan_writer` 二者语义重叠，
    按设计 §2.3「唯一实现」保留 `scan_writer` 为唯一 writer 选择器，
    `present_persist.enabled` **标为废弃**（先在 config 里加 `"_deprecated"` 注释 + 代码侧读口改为
    「若为 false 则报 warning 并忽略」，**不删键**，避免手改 config 的用户直接崩）。
  - 更新 `config.json:7 _note`（现文本「2026-10-07 已切：scan 的 signals 行改由当日 Record.ready 投影」
    与 :9 的 `scan_writer="scan_day"` 自相矛盾，必须改正）。
- **路线 B（不推荐）**：保留 `scan_day`，让 `_rows_by_scan_day` 结束后同步调 `persist_days`。
  —— 代价：判定引擎回到 `scan_day` 门表路径，等于**第二条判定路径**（审计 core B4-2 同族），
  与 §2.3 红线冲突。仅当路线 A 因未知原因不可行时选它，且必须登记为技术债。

**同时要修的连带项**：
1. `rebuild.projection_ledger_refresh` 的「切片无投影」应视为**可恢复状态**而非异常中断——改为
   记录到报告并**允许指纹推进**（否则每次重启都空转，属独立故障源）。
2. 观察灯不可达：`tools/` 里若存在依赖 `confirm_prog_hit>0` 的门禁，修正为「切片缺失 = FAIL」而非
   「指标不达标」。

**验收**：① 切 writer 后跑一天生产（或 dry-run），`monitor_progress` 有非空 progress；
`startup` 指纹能推进；② `pytest` 全绿；③ **必须在 `docs/口径差异报告.md` 登记**：切 writer 会改变
「信号行的判定来源」，历史行的口径与新行不同，须标注。

**风险**：**这是本方案风险最高的一条**——它改变生产判定来源。执行前必须确认：
`scan.py` 的 `_rows_by_record` 分支当前**是否有生产级测试覆盖**（若无，先补一个离线测试再改）。
禁止在没有测试的情况下改 writer。

### P1-3 `run_hold_stop` 到期顺延 off-by-one（跳过一个交易日）

**现象**：`exit_engines.py:156-158` 到期日一字跌停 → `pending_dn=True; exit_d = hold_days`；
`:169` 尾块 `nxt = entry_idx + exit_d + 1`。d 口径为「d=1=入场当日 ⇒ 索引 = entry_idx + d - 1」
（:59、:176 `exit_d = nxt - entry_idx + 1` 自洽）⇒ 顺延起点应为 `entry_idx + hold_days`，
实算 `+hold_days+1` ⇒ **跳过一个交易日**，且报出的 `exit_day` 多 1。

**关键陷阱（必须写进 PR 描述）**：`run_trail_stop`（:343-348）的「持仓到期」写入
**既没有 `d == hold_days` 守卫、也没有 `break`**，靠「每日覆盖、最后一日生效」使 `exit_d`
恰好停在 `hold_days-1`，其同型公式**碰巧正确**。
⇒ **两个引擎各带一处缺陷、互相抵消。只修一个会把另一个的 off-by-one 显形（回归表现：出场提前/推后 1 天）。**

**修法**：
1. 修 `run_hold_stop` 的 `nxt` 公式（去掉多余的 `+1`）；
2. **同批**给 `run_trail_stop` 的到期写入补上 `if d == hold_days: break`，使其与公式对齐而非靠巧合；
3. `defer_force_open:404` 是**同型公式**，语义取决于调用方传入的 `exit_d` 坐标
   （`break.py:963` 调用点需逐笔核对）——**本方案不在本条修它**，登记入 §5，避免把 3 处混成一次改动。

**验收**：新增 `tests/present/test_exit_hold_rollover.py`：构造「到期日一字跌停、翌日可成交」的
合成 bars，断言（a）出场日 = 到期日**次一交易日**、不是再往后一天；（b）`exit_day` 报数与实际索引一致；
（c）同一构造下 `run_trail_stop` 结果**不变**（证明两处修完后抵消关系仍成立）。
再跑 `tmp/_break_equivalence.py` 与 `tmp/_g56_equivalence.py`（设计 §9.2）。

**偏离风险**：改出场会影响所有持仓的出场日 ⇒ **golden 基线可能变**。
处置：若 `tests/golden/freeze.py --check` 不一致，**先判定是「修正了错误」还是「引入了错误」**，
用上面 (c) 的不变性断言裁决；确认是修正则更新基线并在 `docs/口径差异报告.md` 记一笔。

### P1-4 `run_trail_stop` 用当日 high 抬追踪线（日内先视）

**现象**：`exit_engines.py:263-266` 进循环先 `peak = max(peak, bar.high)`；`:314-323`
`trig_t = peak*(1+trail/100); trig = max(trig_t, trig_s); if low <= trig`。
`use_trig_prev` 守卫（:328-332）**只修成交价**（`open > trig_prev` 时 `fill = trig`），**不修触发判定**：
若当日 low 先于 high 出现（日线无法分辨），用当日 high 抬高的线会误触发出场。
模块头 :205 声称「追踪线用开盘时已知峰值防日内先视」——**与实现不符**。

**为什么不偏离**：设计 §8 纪律 1（as-of 不可破）、§9.3 未来扰动法。目标态 §3.3「正偏移=未来函数，双重拒绝」的精神
在出场腿同样适用；且 `exec.replay_sell_intraday`（exec.py:140-160）**已按逐槽推进 peak**（正确），
⇒ 两条腿口径不一致，日线腿**系统性偏早出场**。

**修法**：
- 追踪线必须只用**决策时点已知**的峰值。两种可选口径，需**二选一并登记**：
  - **口径 A（推荐，与盘中腿对齐）**：`peak` 只累积**前一交易日及之前**的 high，
    当日 high 仅在**当日收盘后**（`d` 的下一轮）才纳入 ⇒ 等价于「用开盘时已知峰值」，与 :205 的声明一致。
  - 口径 B（保守放弃追踪优势）：`peak` 完全不含当日 high。
- 触发价与成交价分别用 `trig_prev` / `trig_cur`（现有守卫已支持成交价，只需把**判定**也切到 `trig_prev`）。
- **注意与 P1-3 的耦合**：本条改的是 `:314-348` 一带，与 #3 同文件相邻 ⇒ **两条必须同 PR 或严格前后串行**，
  否则无法判断回归来源。

**验收**：新增 `tests/present/test_trail_stop_asof.py`：
（a）构造「当日 high 创新高、low 未跌破昨峰线」的 bars，断言**不出场**（口径 A）；
（b）未来扰动法：打乱 `bars[D+1:]` 重跑，出场决策逐位一致；
（c）盘中/日线两腿在同一构造上给出**相同出场日**。

**风险**：本条**会改变出场结果**（日线腿变晚出场 ⇒ 收益变化）。必须：
① 更新 golden 基线并登记口径；② 在方案交付说明里明确「修正前后的收益差是修正，不是回归」。

## 6. 方案自身的问题（**执行前必读**）

诚实列出本方案自身的缺陷，避免其他专家把它当成「已完成的修复设计」直接落地：

1. **覆盖不全（最主要问题）**：三份审计约 50 条，本方案只覆盖 **13 条经复核确证**的。
   §5 的数十条**未复核**，其中至少 `prod B-7`（DB UTC 时钟）从证据看**很可能成立且影响生产闸门**，
   本方案因未复核而未纳入。⇒ **本方案不能被引用为「审计问题已全部覆盖」**。
2. **未复核 ≠ 无问题**：修完这 13 条后，系统**不等于**干净。执行者必须理解「已修」与「已审」的区别。
3. **验收依赖真实数据与生产环境**：P0-1（盯盘）、P0-2（writer 切换）、
   P2-11/P2-12（写库语义）**无法靠单测证明**，必须在有备份 + dry-run 的条件下验证。
   本方案给出了条件，但**没有给出验证脚本**——这是缺口。
4. **含行为变更，会改历史统计**：P1-3/4/5/6/8/11/12 都会改变交易集合或出场日，
   ⇒ 一切「修完收益变了」的结论**必须先判断是修正还是回归**，不能直接接受新数字。
   判定方法已给（不变性断言 + 逐笔等价 + 未来扰动），但**执行者仍需人工裁决**。
5. **P1-7（接线 exit.mode）是本方案的技术风险峰值**，且我**没有验证过接线后的行为等价性**——
   我只确认了「当前不生效」与「存在三份同族实现」。接线方案是把既有实现挂到分派器上，
   但 `combo`/`break_combo` 的参数语义是否与 `params:` 段完全对齐，**需要逐字段核对**，可能超出本方案范围。
6. **两份基准文档本身可能已过时**：`自动策略系统设计.md` 日期为 2026-09-24，
   晚于它的变更（2026-10-07 A2、2026-10-09 P6 与市场门方案 A）**未反映在文档中**。
   ⇒ 本方案在个别处（如 canonical trade 字段、`signal_date/buy_mode/trigger` 已废）**以代码为准而非以该文档为准**，
   执行者若发现冲突，**以目标态 + 代码现状为准，并回头修文档**。
7. **未评估工作量与排期**：本方案给出批次与依赖，但**没有工时估算**。
   P0-2 与 P1-7 的实际工作量可能远超其他条目（前者牵动生产判定来源，后者牵动全部策略出场）。
8. **门禁体量风险累积**：`test_kernel_size.py` 的 `PROGRAM_CAP` 现为 1330（2026-10-09 从 1225 上调）。
   P1-7 接线 + P1-8 收敛会使 core 增长 ⇒ **每次上调都要登记理由**，否则门禁会先于功能失败。
