# 领域(domain)在 app/agent 全包中的作用梳理

- **来源/任务**: 用户提问"domain 在整个 agent 目录下的作用,好像只有工具选择在起作用?"
- **署名**: AI 助手(OpenClaw 会话)
- **时间**: 2026-10-14
- **方式**: 只读 grep 全包 + 逐个消费方核对(函数名为锚)

---

## 一、结论先行

「domain/领域」在本包里是**四套并行分类学**,至少 **5 条通道**在影响行为,
工具选择只是最显眼的一条。但用户直觉有坚实依据:
`domain_registry.py` 宣称的"跨层唯一分类学来源、新域接入不改核心"**只兑现了 4 个函数**,
旧编排层(nodes/task_agent/plan_linter)的域通道全数断头,活下来的预选词典
**根本没走 domain_registry**,是自己硬编码的另一份。

## 二、四套域分类学(互不同源,极易张冠李戴)

| 分类学 | 值域 | 定义处 | 消费方 |
|---|---|---|---|
| **工具域** | common/meta/finance/knowledge/capability | `ToolProvider` 扫描目录 + `CAPABILITY_DOMAIN` + `CORE_TOOL_DOMAINS` | 工具分层(`qd_tool_face`)、预选目录、`tool_discovery` 域概览 |
| **数据域** | quote/kline/trend/fundflow/sector/screen/valuation/chip/volume/market/dragon/strategy/intel/capital/knowledge(15 个) | `preselect/tool_preselect.py::DATA_DOMAINS`(硬编码) | lint R1 补位/R4 裁剪、`fallback_domain_tools` 域兜底、`preselect_stats` 空域统计 |
| **追责域** | finance/code/data/general(4 个) | `chain/claims.py::_DOMAIN_KEYWORDS` + `classify_domain()` | 入库闸门 `intake_gate`(domain_enabled)、decisions/claims 落库、`weight_feed` 聚合粒度 |
| **分类学注册表** | DomainSpec(finance/knowledge) | `domain_registry.py` + `tools/*/domain_meta.py` | 仅剩 4 个函数活着(见下) |

⚠️ 同名不同义:追责域的 "finance" 与工具域的 "finance" 不是一回事(前者是"该不该追责",
后者是"工具住在哪个目录")。weight 层的 `domain` 键 = **追责域**。

## 三、5 条在起作用的通道

1. **工具面分级与预选**(用户看到的那条,最活跃)
   `CORE_TOOL_DOMAINS`(common/meta 必注入)→ 按需分层;`detect_domains` 词典驱动
   lint 补位/裁剪/域兜底;capability 来源域让位(域内优先)。
2. **追责入库闸门 + domain 粒度权重闭环**(实打实在跑,不止工具选择)
   `classify_domain` → `intake_gate`(`domain_enabled` 读 `qd_domain_resolvers` 表,
   库缺用内置 `DOMAIN_POLICY`,v1 只开 finance)→ decisions/claims 带 domain →
   `weight_feed` 按 domain 聚合(EMA 慢调)→ `qd_agent_weights(layer='domain')` →
   `weight_hints`(唯一读口,TTL 600s)→ ①预选 `history_hint` ②技能排序乘子 ×(0.5+0.5w)。
3. **时间解析口径**:`resolvers/time` 用 `trading_calendar_domains()` 决定"明天"是
   交易日还是自然日;`word_domain_hints()` 无实体时语汇倒推域。
4. **追溯链名归一**:`normalize_chain_name`/`strip_entity`/`classify_verb` →
   `utils/tracing` + `chain/store` + `skill_brewer`(链名 domain+verb+noun → chain 权重)。
5. **技能选择域信号**(弱):`qd_service._FINANCE_GATE` + bridge 实体→域注入 +
   domain 权重体系间接乘子。

## 四、死件与残迹(用户的直觉落点)

## 五、与用户直觉的对照

- ✅ 对:**"预选/工具选择用的域"确实是唯一被"选择"消费的域**——而且它走的是
  `tool_preselect` 硬编码词典,不是 domain_registry。domain_registry 的"新域接入
  不改核心"承诺大半未兑现,只剩实体→域、词→域、交易日口径、链名归一 4 个函数。
- ❌ 不止:追责闭环(domain 闸门→权重→反哺)与时间解析(交易日口径)是真通道,
  不是摆设。

## 六、建议(待拍板,不建议现在动)

1. **死件处置二选一**:①`domain_meta._DATA_DOMAINS` 等死 API 归档/删除;
   ②或把 `tool_preselect.DATA_DOMAINS` 迁回 domain_registry 做单源(动活词典,
   需 P9 基线对拍,成本高于①)。短期推荐①+修幻觉引用注释。
2. **四套分类学对照表**入 docs(本文第二节),防后人把追责域 finance 与工具域 finance 混用。
3. `weight_feed` 的 domain 粒度本就是设计上限(§3.5:resolutions 不带 tool/skill 归因),
   不必"升级"——但 P3 之后条件格(condition_key)接上时注意别把两套粒度混写。
