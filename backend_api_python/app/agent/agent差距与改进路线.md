## A. 规划质量无代码强保证

**现状**：规划由 mimo 原版循环承载（模型自规划 + `update_plan` 清单工具 + system_template 纪律蒸馏）。旧的 phases/plan_linter/plan_critic 已随编排层退役归档。
**差距**：规划质量完全依赖 prompt 和模型自觉，**prompt 一次误改就能让规划回退**，且无代码级兜底（runaway 计划、缺步骤、工具面漂移都只能靠肉眼发现）。
**方案**（三选一或组合，按回退严重度升级）：
1. prompt 回归套件（`scripts/qd_prompt_eval.py` + `prompt_tasks.yaml`）**补规划类任务**：多步骤任务断言"有计划、步骤可执行、有验收动作"；
2. run 级轻校验：run 结束时检查 `update_plan` 状态（存在 in_progress 残留 → 落 trace 告警），只告警不拦截；
3. 若实测规划回退严重，从 `del/`/旧仓库恢复 `plan_linter`（纯函数零依赖，归档时已确认可回滚）做**输出侧**校验，不恢复 phases 编排。
**验收**：套件含 ≥5 个规划任务；连续两次 prompt 改动的评测 diff 可见规划质量变化。

## B. 执行型技能无子 agent 分发通道

**现状**：`skills/market_screener/run.py`、`strategy_debug/run.py` 是执行型流水线，暂不入工具面（skill_tools 注释已标注）；渐进式加载（目录+按需读）已就位，但那是"读方法论"，不是"派活"。mimo 原版 `task` 子 agent 工具在，无技能分发约定。
**差距**：重活（全市场扫描 5000+ 标的）全压主 agent 上下文，token 和注意力双输；主 agent 应只拿结论。
**方案**：
1. 新增 `run_skill(name, args)` 工具（能力层低优先级派发同款护栏：超时/体积/写前缀复核）；
2. system_template 补分发纪律："扫描/回测等批量任务 → task 子 agent 执行 run.py，只回报结论摘要"；
3. 子 agent 产物约定：结论 JSON 落 `tmp/`，主 agent 读摘要——上下文 O(摘要) 而非 O(全量)。
**验收**：一次全市场筛选任务，主 agent 消耗 ≤ 无分发方案的 40%，结论质量不降（对照 chain/evaluator 评分）。

## C. 能力级评测体系缺失（P0，其余多项依赖它）

**现状**：167 项 smoke + prompt 套件都是**回归级**（防"改坏"），没有"选股分析质量 82 分"这种**能力标尺**。chain/evaluator 的评分口径和 qd_traces 样本积累是现成地基。
**差距**：所有调优（E/F/G/K）都无标尺可对；升级模型/prompt 后"更好还是更坏"只能靠感觉。
**方案**：
1. 从 qd_traces 挑 20~50 个真实任务（覆盖：个股分析/选股/复盘/交易确认/通用问答）固定为 benchmark 集；
2. 评分维度复用 evaluator 口径 + 人工标注基线分（每个任务标注"好答案的最低要求"）；
3. 跑分工具：`python -m scripts.qd_bench` 输出总分+分项，落库可对比（qd_traces 已有树结构可挂）。
**验收**：任意改动后一键出分，历史曲线可查；两人对同批输出的评分一致率 ≥80%。

## D. 会话上下文不跨进程持久化

**现状**：`QDAgentService._sessions` 进程内 dict，messages 天然多轮但**重启即失忆**；PostgresMemory 有历史（记忆层），但消息级续承（对话中段、工具中间结果）不持久。
**差距**：部署重启/发版 = 用户对话断片；多 worker 部署时同 session 路由不到同进程也会断。
**方案**：
1. 会话快照：run 结束把 messages 序列化落 PG（复用 qd_agent_messages 表或新表），启动/换 worker 时恢复；
2. 配合 compaction：快照前先压缩（保留数字/结论/未完事项——compaction_summary_prompt 已是金融化定制），控制快照体积；
3. TTL 与 memory 层对齐（现 604800s）。
**验收**：kill 进程重启后同 session 续聊，上下文连续（可用 smoke 风格断言：第二进程能引用第一进程的对话内容）。

## E. Few-shot 金例注入

**现状**：未做。qd_traces 里跑批样本在积累。
**差距**：好案例的经验没有进入 prompt，每次都从零发挥。
**方案**：C 建立评分后，按任务类型各挑 2~3 个高分案例（输入+输出骨架，脱敏数字），动态注入 instance_template；按权重反馈轮换（低分案例淘汰）。
**验收**：同类任务金例注入后 evaluator 评分均值上升；单例注入成本 ≤ 500 tokens。

## F. 参数精调

**现状**：temperature=0.1、max_tokens=16384、step=AGENT_MAX_STEPS×3、技能阈值=2、预取相关度闸门=2——全是拍脑袋初值。
**差距**：无网格对比，不知道这些数是不是局部最优。
**方案**：以 C 的 benchmark 为标尺，对上述 5 个参数做单变量扫描（每次只动一个，跑分对比）；结论写回 `.env.example` 注释。
**验收**：每个参数有数据支撑的推荐值和敏感度说明（"±1 档掉几分"）。

## G. 胜率反哺扩展（部分落地）

**现状**：`chain/weight_feed`（追责→权重喂数）+ `weight_hints`（四层快照）已落地；技能匹配里权重只做 **tie-break**（词典分打平时才生效）。
**差距**：权重的杠杆太弱——一个历史胜率 0.2 的技能和 0.9 的技能，在词典分不同时排序完全由词典分决定。
**方案**：权重升级为**排序分乘子**（score × (0.5 + 0.5×weight)），配 MIN_SAMPLES 慢调纪律（已有）防小样本误伤；tool_preselect 同理接入 preselect_stats（已留口）。
**验收**：构造胜率差异明显的技能对，断言高胜率者稳定排前；冷启动（无数据）行为与现状一致。

## H. 成本/时延 SLO

**现状**：只有步数预算（step_limit）；token/费用/时延无硬约束，`GlobalModelStats` 有计数但只用于 wrap-up 提示。
**差距**：一个任务跑飞 = 烧钱无上限；长任务挤占 worker 无降级。
**方案**：
1. run 级 token/费用预算（env：`QD_TOKEN_BUDGET`/`QD_COST_BUDGET`），超限触发与步数同款的"截断收尾"（已验证的独立预算机制可复用）；
2. 时延软 SLO：超时降级为"已有数据出结论 + 注明未完成部分"（比空结果好）。
**验收**：预算超限的 run 返回可读降级文案而非异常；预算事件落 trace（repro 字段已有 token 统计位）。

## I. 超大技能 TL;DR 头部（内容工程）

**现状**：渐进式加载（目录+首段+按需读路标）已上线；但 `auto_stock-analyze`（5.2k 字/6 节）等大技能仍靠截断出首段。
**差距**：截断点是字数不是语义，首段未必是最该看的（何时用/核心流程/硬约束）。
**方案**：给每个 ≥3k 字的 SKILL.md 加 300~500 字 TL;DR 头部（何时用/三步主流程/三条硬约束），`_skill_block` 优先注入 TL;DR+目录。**内容由技能作者写**（方法论取舍是业务判断，代码不猜）。
**验收**：注入块 ≤1200 字符且覆盖"何时用/主流程/硬约束"三要素。

## J. 发布工程收尾

**现状**：smoke 161/167，6 个失败=环境缺件：①`DATABASE_URL` 未配（PG 入库×2）②股票名录库不可用（resolver×2）③`del/agent_formatters_20261001` 未入 git（归档检查×2）④`capabilities/admission.json` 未入 git（工具面 95 断言，缺清单时只有 61）。
**差距**：新环境 clone 即过不了自家 smoke；审计件（admission.json）游离在版本控制外，机器丢了=能力清单丢了。
**方案**：
1. `admission.json` 入库（它是人工审核件，本就该版本化；如含敏感函数名可出脱敏版+完整版放私有存储）；
2. `del/` 归档目录入库（或改 smoke 断言为"归档在 git 历史可查"）；
3. smoke 增加 `--with-env` 模式：无 PG 时自动 skip 而非 fail（CI 和本地分开计数）；
4. dashscope 方言若 openai_chat 不兼容，补自定义 Model 子类（接口仅 query()，半天活）。
**验收**：干净 clone + `pip install -r requirements.txt` + 无 PG 环境 → smoke 全绿（skip 计入）；带 PG 环境 → 167/167。

## K. 工具预选从启发式到可学习

**现状**：`tool_preselect.py`（25 必注入 + 63 按需，21.2k→8.7k/轮）用 token 倒排索引+域词典，纯启发式；`preselect_stats.py` 已留统计口。
**差距**：同义问法/新黑话（"打板""埋伏"）召回差；选错工具面 = 该用的工具不在场。
**方案**：preselect_stats 攒「任务→实际调用工具」对，周级离线算共现权重，预选排序加权；召回不足时退化为现启发式（永不更差）。
**验收**：held-out 任务上预选召回率（实际调用工具 ∈ 预选面）≥95%，token 不回升。

## L. 备选路线 B 存档（MiMo-Code 大脑）

**现状**：已评估未采纳（2026-10-01 定稿路线 A=white-box）。MiMo-Code 本体有持久记忆/上下文重建//dream，但金融工具需 MCP 化、行为偏软件工程。
**何时重启**：出现"长程编码类子代理"需求（策略代码生成/回测工程化），或路线 A 的规划/记忆短板（A/D）修完仍不达标。
