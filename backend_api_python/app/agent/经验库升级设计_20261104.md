# 经验库升级设计：多轮假设、条件关系与交易结果闭环

> **来源**：用户与 Copilot 关于经验库升级的连续讨论
> **任务**：将 run 级案例记忆升级为可检索、可细化、可回测的经验系统，并纳入工具效果反馈与盘中数据容量设计
> **整理时间**：2026-11-04 11:26（Asia/Shanghai）
> **性质**：实施设计提案；本文不代表数据库已变更或功能已实现

## 1. 目标与边界

### 1.1 目标

构建一个数据库驱动的经验闭环，使系统能够：

1. 从单轮及多轮 agent 运行中提取有出处的经验候选；
2. 将经验表达为带适用条件、时间点、关联关系及证据质量的可检验假设；
3. 记录全市场选股的候选全集、选择/排除决策和决策时可见的数据；
4. 对每项假设按 T+1、T+3、T+5 等交易日窗口进行无未来信息泄漏的评估；
5. 把工具调用质量与策略/市场经验纳入同一证据基础，但保持不同指标和归因单位；
6. 支持事件驱动的盘中经验，同时避免复制所有行情 tick 或分钟数据造成数据库膨胀；
7. 通过 LLM 提议拆分、合并、修订经验，由确定性验证和回测决定经验状态，不允许 LLM 自行认证有效性。

### 1.2 非目标

- 不承诺“完美预测”或保证经验在未来有效；目标是可审计、可重放、可证伪和可撤回。
- 不把一份 `SKILL.md` 中所有文字都当作交易经验。工具契约、指标定义、流程纪律与统计经验需要分层。
- 不以 LLM 的文本相似度、用户赞同或单个成功案例作为经验有效性的判据。
- 不为每条经验自动生成一份新的活跃 `SKILL.md`。技能文档说明稳定流程；经验以数据库中的版本化对象管理。
- 不将市场原始分钟线/tick 全量复制到 agent 经验库。原始行情仍由行情数据层负责。

## 2. 核心抽象：从案例转为有时间边界的假设

### 2.1 知识类型

| 类型 | 示例 | 维护方式 | 是否直接进入回测 |
|---|---|---|---|
| 定义/数据契约 | MACD 算法定义、金额单位、交易日口径 | 代码/工具契约版本化 | 不作为策略假设 |
| 流程/纪律 | 缺数据时如何报告、先取哪些证据 | `SKILL.md` 或共享流程规范 | 不直接作为收益假设 |
| 经验假设 | 某条件组合下 T+3 超额收益是否改善 | 数据库候选、版本化、可回测 | 是 |
| 运行案例 | 某次会话的工具调用、最终答复、错误与成本 | 作为经验提取原料和审计记录 | 需提取为假设后再评估 |

### 2.2 经验假设定义

一项经验不是一句自然语言结论，而是版本化、结构化的可证伪对象，至少包含：

- **scope**：市场、策略/任务类型、标的范围、持有窗口、盘前/盘中/盘后等时段；
- **when/known-at**：经验所依据的信息截止时点，所有输入必须在该时点已可得；
- **conditions**：特征、比较符、阈值、缺失值策略及特征来源；
- **hypothesis**：预期方向或相对基准的收益/风险变化；可以是数值目标或明确的方向性预测；
- **outcomes**：T+1/T+3/T+5 等分别评估，不用一个总标签替代；
- **evidence**：样本数、时间区间、交易日覆盖、基准、收益分布、回撤、置信区间和交易成本口径；
- **lineage**：源会话/turn/trace、原技能及段落、输入快照、代码/数据/模型版本；
- **state**：`candidate`、`testing`、`active`、`degraded`、`rejected`、`expired`；
- **relations**：拆分自、细化、支持、冲突、依赖、被更新等有向关系；
- **lifecycle**：创建者、LLM 提议版本、人工审核、评估版本、激活/撤回时间及理由。

条件以可执行 JSON/DSL 表示；自然语言仅作为解释，不作为回测执行条件。特征必须使用有 schema/version 的名称，例如 `sector_relative_strength_5d@v2`，避免同名异义。

### 2.3 条件组合与避免组合爆炸

MACD 金叉不能脱离板块热度、资金、筹码、波动状态而自动视为有效。经验评估采取逐层条件检验：

1. 建立整体基线；
2. 检验单一条件是否产生增量；
3. 只有预先提出且样本允许时，检验条件交互（例如 MACD 金叉 × 板块相对强度）；
4. 对多重尝试和反复拆分进行多重检验/过拟合控制，并保留时间外验证；
5. 低样本时向总体先验收缩，标记证据不足，而不是复制出更多“已验证”规则；
6. 规则适用范围变化必须产生新版本，不能覆盖旧的评估结果。

文本 embedding/关键词只用于找候选经验；相关性和效用最终由结构化条件覆盖、增量效果、样本量和时间外结果来衡量。统计共现不得描述为因果。

## 3. 多轮会话和判断版本

### 3.1 会话不是经验的唯一单位

一次用户问题可能跨多个 agent run 才解决。系统需要在现有 `session_id`/trace/run 之上增加稳定的**问题过程 ID**（`workstream_id` 或 `case_thread_id`），把属于同一问题的多轮事件关联起来。会话可包含多个独立问题；问题过程也可能跨会话继续，关联关系必须明确而不能仅凭相邻时间推断。

每轮追加事件，不覆写历史：

- 用户补充的事实、目标、约束或纠正；
- 工具观察及其 source/as-of；
- agent 的假设、证据和置信状态；
- 质疑、冲突证据、检索/工具失败；
- 假设变更及其触发证据；
- 最终状态（解决、暂停、放弃、待观察）。

### 3.2 假设版本与信息时点

每次重要结论变化形成新的 `hypothesis_version`：

- 记录 `valid_as_of` / `information_cutoff`；
- 记录使用的数据快照 ID 和此前可见的证据；
- 指向被支持、被修正或被否定的前序版本；
- 记录新增证据是什么，以及为什么足以改变判断；
- 后续新增的信息不得回写到旧版本的输入集合。

因此，000915 的例子应保留为至少两个不同的信息集：业绩公布时依据当时信息形成的偏空假设；后来出现连续下跌、筹码/抛压证据及增持消息后形成的新假设。后一版本可以更新前一版本，但不能把新消息倒灌到前一版本的正确性评估中。

“筹码上端没有松动”“18.5 附近抛压小”等自然语言需转换为可观测特征，并注明估算来源、时点和不确定性；若没有可复算数据，只能留作待验证叙述，不能充当已证事实。

### 3.3 用户反馈语义

保存用户信息的类型/来源：新事实、事实纠正、偏好、质疑、目标调整或认可。用户认可/否定可以用于流程质量或待核验线索，但不是市场收益标签，也不能直接把经验置为 `active`/`rejected`。

## 4. 全市场选股与真实回测闭环

### 4.1 必须记录候选全集

全市场筛选的评估单位不能只有最终推荐的少数股票。每次 selection run 应保存：

- 扫描范围/候选池来源、策略和参数版本；
- 候选全集或明确的可重建来源，以及被排除/未入选状态；
- 每只候选在当时的 rank、过滤原因、推荐/观察/排除决策；
- 决策时可用特征、缺失项、数据源/数据时点和快照版本；
- 本次实际调用的经验版本及其对排序/判断的贡献；
- 使用模型、工具版本、代码版本和回测/评估口径。

记录未入选候选是估计选择偏差和比较排序策略的必要条件。若不能保存完整市场逐股特征，至少要保存可复建的 universe 定义与数据版本，并为最终候选及决策边界附近的候选保留完整 feature snapshot；抽样/压缩规则必须版本化。

### 4.2 T+N 标签定义

- T+1/T+3/T+5 均按 `chain/label_spec.py` 的交易日窗口真源计算，不用自然日近似。
- 每个 horizon 独立产生结果；目标价/止损/持有逻辑属于不同 outcome，不用单一 `correct` 混合。
- 保存理论价格结果与可交易模拟结果的区别。模拟必须考虑次日开盘/可成交价、涨跌停无法成交、停牌、滑点、佣金、印花税、公司行动和复权口径。
- 对选股组合和策略，同时报告基准超额收益、收益分布、尾部损失、最大回撤、换手和容量，不只看胜率。
- 训练期、调参期和时间外测试区间按时间顺序隔离；重叠持有窗口应按 run/日期聚类或使用适当统计修正。
- 特征输入严格 as-of：公告发布日期/可见时点、行情快照时间与决策时间不一致时不得使用。
- 评估状态要区分 `pending_maturity`、`not_applicable`、`undecidable`、`data_missing`、`infra_failure`、`labeled`，避免所有非正确/错误案例永久堆在 `pending`。

### 4.3 经验如何影响线上选股

线上仅消费已 `active` 且未过期的经验版本。每次调用记录：

- 哪些经验进入候选/被检查/被应用；
- 经验未应用的原因（条件不符、数据缺失、版本不兼容、关闭/过期）；
- 应用前后的候选排序/分数或决策变化（尽可能以影子/反事实方式记录）；
- 选中和未选中的结果，用于评估经验的增量贡献，而不是只统计“应用后被选中股票的涨跌”。

新经验先以 shadow 模式运行，不改变生产决策；通过样本与时间外效果门槛、数据质量审查和版本审核后方可激活。激活条件和阈值应由配置/政策版本管理，并能一键停用或回滚。

## 5. 工具权重闭环与经验库的关系

### 5.1 建议：统一证据基础，不混为一种权重

工具权重应纳入同一套**运行证据、归因和评估平台**，但不能把工具表现与交易经验直接合成一个分数或共用一个标签：

- **市场/策略经验**回答：在某类市场条件下，某个条件组合是否改善决策结果；
- **工具效用**回答：在某类任务/输入下，工具是否成功、及时、覆盖必要证据、数据是否准确且对结论有增量；
- **技能效果**回答：某个技能版本在特定任务范围内是否改善结果；
- **编排/链路效果**回答：某种工具/技能组合是否降低成本或提高任务完成质量。

这些结果可以进入共同的证据仓库，并共享 trace、版本、时间、曝光和 outcome；各自仍有独立的评估目标、样本门槛、量纲、读侧权重和限幅策略。工具被调用不等于有效，未被调用也不等于失败；应记录曝光漏斗、调用成功率、数据新鲜度、相关性、延迟/成本和可归因的下游增量。多工具共同完成任务且无法唯一归因时，标为不可归因，不强行分摊功劳。

### 5.2 现有权重/事件链迁移策略

仓库已有 `qd_agent_weights`（旧链/domain 等）和 `qd_skill_feedback`（版本级技能反馈），应先核实实际写入、消费口和语义，再决定迁移。设计方向：

1. 不再新建第三套彼此不知情的权重表；
2. 将工具、技能、策略/经验评估统一汇入可追溯的 evidence/event 层；
3. 保留 typed aggregate/read model（如 tool reliability、skill outcome、strategy alpha），各自按适合的指标计算；
4. 迁移阶段双写/影子比较，核对样本去重、时间窗、状态语义和消费行为；
5. 验证新读侧后，逐步将既有权重消费者迁移到统一服务；保留旧表只读审计/回滚期，明确弃用时间；
6. 任何权重不得跨市场/任务类型无条件泛化；低样本时回落中性权重。

因此答案是：**工具权重闭环应该统一到经验系统的证据闭环中，但工具权重本身不应被折叠成“市场经验权重”。**

## 6. 盘中实时经验与数据库容量

### 6.1 事件驱动，而非逐 tick 写经验表

经验库只保存决策需要的行情/特征快照和引用，不复制行情库全部原始数据。建议的触发点：

- agent 首次形成交易假设；
- 重要价格/量能/板块状态跨越预先定义的阈值；
- 关键新闻/公告到达且被本轮实际使用；
- 用户补充/质疑导致假设更新；
- 执行/复核/止损/目标条件触发。

同一假设版本在相同条件下重复观察可按时间桶去重或只保存变化点；采样规则要版本化。高频 tick/1m 原始序列继续留在行情数据层，由 `snapshot_ref`、数据版本和 as-of 时间引用；仅对无法从源数据可靠重建的派生特征做紧凑快照。

### 6.2 存储分层和容量控制

- **在线关系库**：运行元数据、经验定义/版本/关系、索引、评估摘要、活跃线上快照引用。
- **特征/行情存储**：高体积全市场或分钟级快照使用独立分区表/列式存储/对象存储；关系库保留 URI/key、schema/version、时间范围、校验和。
- **审计原始事件**：追加写，按日期和市场分区；压缩、冷热分层、保留期按用途设定。
- **查询索引**：按经验状态/域/任务、特征键、适用时段、horizon、instrument/date、版本关系等建立有选择性的索引；不对高基数字段盲目建索引。
- **保留策略**：活跃经验和聚合长期保留；原始逐轮/特征明细按审计及重放需求冷热归档；不删除仍被活跃经验引用的数据版本。
- **写入方式**：评估/向量化/LLM 提取均异步批处理；在线主链只写轻量事件或队列，不等待长回测和 LLM 复盘。
- **防膨胀**：对快照大小、每次筛选候选数量、盘中变化点频率和保留期限设配额/监控；超限显式记录采样或归档，不静默丢弃。

### 6.3 盘中标签

盘中策略若需要分钟级结果，应单独定义 horizon（如决策后 N 分钟/收盘），与交易日 T+1/T+3/T+5 分开存储。记录交易阶段、报价/成交可得性、盘口/滑点假设、午休、涨跌停和停牌状态；分钟级标签不能用日线收盘结果冒充。`bar_freq`、交易时段规则和特征版本均写入快照。

## 7. 建议的 PostgreSQL 逻辑数据模型

以下为逻辑设计，不是可直接执行的最终 migration。分阶段实施时应沿用仓库迁移规范，先验证已有表、索引、保留期和数据库版本。

### 7.1 核心表

| 表 | 粒度 | 关键字段/用途 |
|---|---|---|
| `qd_workstreams` | 一个跨轮问题过程 | `workstream_id`、根 session/run、任务类型、开始/结束、终态 |
| `qd_workstream_events` | 一条追加事件 | `event_id`、workstream、run/turn、事件类型、时间、source/as-of、payload/ref；按时间分区 |
| `qd_hypotheses` | 一个稳定假设家族 | 假设类型、领域、创建来源、当前状态/版本指针 |
| `qd_hypothesis_versions` | 一个不可变假设版本 | 父版本、条件 DSL、预测、scope、information cutoff、特征/schema 版本、lineage、LLM/审核信息 |
| `qd_hypothesis_relations` | 两个假设版本间一条有向关系 | `refines/supports/conflicts/updates/depends_on/derived_from`、证据来源、时间 |
| `qd_decision_runs` | 一次筛选/分析决策 | as-of、市场阶段、universe/策略/代码/数据版本、工作流关联 |
| `qd_decision_candidates` | 一次决策中的一个标的 | code、选择状态、rank、理由、compact feature JSON、snapshot ref；大表按日期分区 |
| `qd_experience_exposures` | 一次经验/工具/技能的曝光或应用 | decision/run、类型/id/version、eligible/exposed/applied、贡献/未应用原因 |
| `qd_experience_evaluations` | 一次版本 × horizon × 评估方案的结果 | 样本/覆盖区间、收益分布、基准超额、风险、成本、置信区间、政策版本、结果状态 |
| `qd_tool_observations` | 一次工具调用及其质量 | 工具版本、参数/输出引用、成功/错误、新鲜度、延迟、token/成本、下游归因状态 |

现有 `qd_agent_cases` 保留为 run 级案例/提取原料，逐步补充到 `workstream_id`/`decision_run_id` 的可空关联；不直接把它扩成存全部分钟数据的万能 JSON 表。现有 `qd_agent_traces`、claim/resolution 和 `qd_skill_selection_events` 是迁移/关联的重要来源。

### 7.2 约束与索引原则

- 假设版本不可变；修改产生新版本，版本号/唯一键保证同一假设族内幂等。
- 曝光、回测和标签写入必须有稳定唯一键，重试不重复计样本。
- 外键删除策略保护仍被经验、评估和审计引用的历史记录；归档通过引用迁移完成。
- 大表优先按 `event_date`/`trade_date` 做时间分区；按实际查询路径评估组合索引和 BRIN，不预先为每个 JSON 字段建立 GIN。
- 条件 JSON 保持小而结构化；大数组/分钟序列放外部 snapshot store。
- 使用 PostgreSQL declarative partitioning 前先验证当前 16 版本、备份/恢复流程、分区维护自动化和查询计划。

## 8. LLM 多轮拆解与发布流程

1. **提取**：从一个完整 workstream 汇总事件时间线；LLM 仅生成候选条件、预测、证据引用和不确定点。
2. **验证结构**：schema validator 检查字段、引用是否存在、时间顺序、特征是否可用、DSL 是否可执行。
3. **去重/关联**：检索相近假设家族；由确定性比较 + LLM 辅助给出关系提议，所有关系带证据，不因语义相似自动合并。
4. **回测计划**：锁定输入数据/as-of、候选范围、horizons、基准、成本、分割方案和统计政策版本。
5. **执行**：异步跑历史/滚动/时间外回测，记录完整评估 manifest 和结果引用。
6. **复盘**：LLM 基于结构化结果提出细化/拆分/合并/淘汰；不允许直接写 active 状态。
7. **发布**：候选由规则门槛和审核流程批准为 shadow/active；记录批准者/策略和生效时间。
8. **线上监控**：监控 drift、样本量、实际效果和数据质量；退化或过期后自动降级/停用，保留历史状态。

若回测输出显示条件组合没带来稳定增量，应合并回父经验或拒绝该拆分。LLM 生成的经验版本、prompt/model 版本和输入证据都需保留，确保同一提取任务可审计。

## 9. `pending` 状态治理

当前案例库的大量 `pending` 由写入范围宽于股票验证范围、缺股票代码案例仍被记录、方向中性/不可判案例没有终态等因素造成。新设计必须区分：

- `pending_maturity`：确实有明确标的/horizon，结果窗口未成熟；
- `pending_evaluation`：窗口已成熟但评估任务尚未完成；
- `labeled`：结果已计算并附 outcome；
- `not_applicable`：非可回测运行/无市场预测；
- `undecidable`：现有证据不能给出正确/错误；
- `data_missing`：行情或快照缺失；
- `infra_failure`：回测/存储/工具基础设施失败；
- `unattributable`：多技能/多经验无法诚实分配。

不能把不可评估标签当成 `incorrect`，也不能为了降低 pending 数量而伪造 `correct`。存量迁移先只读分类和报告；确认规则、抽样审查后再按新状态迁移，旧 `outcome.label` 保留可追溯映射。

### 阶段 0：现状盘点与数据质量（先做）

### 阶段 1：统一证据/运行关联

- 验收：同一问题跨轮可重建；回放不会读取决策时点之后的数据；候选选择漏斗可核对。

- 从 `stock-analyzer`/`market-screener` 提取少量人工审阅的候选假设，作为迁移试点。

### 阶段 3：多窗口与时间外评估

- 验收：使用已知样例可复算；严格 as-of；同一评估重跑幂等；未来数据泄漏测试通过。

### 阶段 4：盘中快照与容量治理

- 事件/状态变化触发快照，原始行情留在行情存储层；
- 评估分区大小、索引、保留期、归档、查询延迟与备份恢复。

### 阶段 5：影子经验与受控发布

- LLM 提取和修订仅写候选版本；回测、人工审核和影子观察通过后才激活。
- 线上记录经验曝光和反事实边界；按 domain/market regime/horizon 监控。
- 工具权重与策略经验分开评估、共享证据和 traceability；低样本中性，失效可回滚。
- 验收：能解释经验为何被应用；能比较应用/未应用结果；停用后历史回测不变；新旧权重读侧可比并可回滚。

## 13. 设计审查：主要瓶颈与跨领域扩展

> **补充来源**：用户追问“新经验设计还有哪些瓶颈、是否可以扩展到别的领域”
> **补充时间**：2026-11-04 11:32（Asia/Shanghai）
> **性质**：对本文设计提案的增量审查，不表示相关能力已实现

### 13.1 结论

该设计可扩展到其他领域，但当前版本仍是**金融用例驱动的共享平台提案**，还不能直接视为领域无关的通用实现：

- `workstream/event/evidence/version/relation/evaluation-run` 等可作为跨领域共用核心；
- 特征、条件、成熟规则、结果口径和验证器必须由领域插件/adapter 定义；
- T+N、股票候选全集、交易成本、板块/筹码和可成交回测均属于金融域语义，不应下沉为所有经验的强制字段或默认 evaluator。

仓库已有一定可复用基础：claims 中有领域策略配置，resolver 以 `_RESOLVERS` 分派，但目前只实现 finance；skill selection feedback 有候选/曝光/执行/标签漏斗。它们证明域配置和 typed feedback 可行，但**配置表有域名不等于该域的提取、结果标签和 evaluator 已实现**。例如当前 `_RESOLVERS` 只有 finance，因此其他域启用时仍会得到明确的“resolver 尚未实现”结果。

### 13.2 最高优先级瓶颈（建表前必须补齐）

1. **领域中立的结果契约尚未定义。** 当前假设示例偏向预测收益，无法自然表达代码任务的测试通过、数据查询的 schema/数值正确性、客服任务的解决率与时长等。必须将 outcome 定义成有版本的类型化结果，并允许一个经验有多个互不混算的 outcome 指标。
2. **点时数据可复现依赖仍未落到契约。** `snapshot_ref` 只有在行情/公告/特征数据可按历史 as-of 读取、版本稳定且不会被上游修订覆盖时才有价值。需要明确 snapshot manifest、内容哈希、源数据修订策略与重建失败状态；否则“无未来泄漏”无法审计。
3. **选择偏差仍有残余。** 保存候选全集是必要条件，但还需记录候选生成器的覆盖边界、过滤/截断规则和未进入候选池的原因。若 universe 本身漏掉后来表现好的股票，只评估候选全集仍会高估系统效果。
4. **多轮 workstream 关联没有可靠的身份/分叉协议。** 相同会话可有多个问题；同一问题可跨会话继续；用户也可能纠正或撤回关联。需要显式 `workstream_id` 传递、分叉/合并事件和关联置信度，自动相似匹配只能给候选，不能静默合并。
5. **经验 DSL 的安全与演进未具体化。** 需定义受限语法、特征类型/单位、空值语义、比较与窗口操作、运行预算和兼容性规则；禁止执行 LLM 生成的任意 SQL/Python。DSL/schema 升级需有迁移或旧版 evaluator 保留策略。
6. **统计发布门槛尚未可执行。** “样本够、效果稳定、时间外通过”仍是原则。需要指定按域/目标的统计政策版本、置信区间或贝叶斯收缩、基准、风险约束、多重检验/研究者自由度控制、最小经济显著性和停止规则。不得设一套全局样本数阈值覆盖不同域。
7. **关系图可能无限扩张或产生循环。** `supports/conflicts/updates` 可构成一般有向图；`derived_from/refines` 应保持可审计的无环 lineage。关系需要唯一性、状态、有效期和证据引用；候选关系不能自动改变线上检索优先级。
8. **容量与查询成本没有量化基线。** 文档提出分区、冷热存储和对象引用，但尚无每次筛选候选数、盘中事件频率、每条快照尺寸、日/年增长、保留期、检索 SLA 和恢复目标的估算。未完成压测前不能确定 JSONB/分区/外部存储的具体比例。
9. **线上经验检索尚缺冲突解决和可解释排序。** 多条经验可能适用范围重叠、结论冲突、版本新旧不同。读取时要按域/任务/feature schema/horizon/state 过滤，再按证据质量、适用性和时效排序；冲突经验应并列呈现或交给显式组合器，不可仅取 top-k 相似文本。
10. **经验收益归因比结果标签更难。** 一次决策可能同时使用多个经验、技能和工具；只记录“被使用”无法估计增量效果。需要 shadow/对照/反事实评估，记录曝光概率和排序变化；无法识别因果贡献时报告关联而不是分摊权重。
11. **LLM 自动提炼有成本与污染风险。** 需限定触发条件（问题收束、用户显式复盘、达到样本量/新型失败等），对原始证据做引用校验、脱敏、提示注入隔离和 token 预算控制。大量低价值候选应被批量聚类或拒绝，而不是每轮生成经验。
12. **生命周期维护未闭合。** 除 `active/degraded/expired` 外，还要说明数据源/特征版本停用、域政策变化、回测代码修复或历史数据重述时如何使结果失效并重算；任何重算需产生新 evaluation version，不能覆盖旧结论。

上述项目中，1–6 是进入可回测 MVP 的阻塞项；7–12 可在影子阶段建设，但在自动激活前必须有对应治理。

### 13.3 跨领域架构：共享骨架 + 领域插件

建议经验记录采用两层契约：

**共享核心信封（所有领域一致）**

- `experience_id/version/domain/task_type/status`；
- `scope`、`conditions`（引用版本化 schema）和自然语言解释；
- `known_at`、`created_at`、有效期；
- evidence/lineage/workstream/decision/exposure 引用；
- relation edges；
- 一个或多个带 `metric_id`、`metric_version`、`evaluation_policy_id` 的 outcomes；
- 提取模型、prompt、验证器和回测器版本。

**领域插件契约（必须显式注册）**

每个领域提供独立的 `DomainAdapter`，至少定义：

1. `task_classifier`：判断任务类型和是否适合提取经验；
2. `feature_registry`：允许的特征、单位、时间语义、来源与缺失值规则；
3. `claim/experience_schema`：该域可表达的假设种类与 DSL 验证；
4. `outcome_resolver`：确定结果如何观察、何时成熟、何时不可判；
5. `evaluation_policy`：指标、基准、成本、统计门槛、时间切分；
6. `retrieval_policy`：适用域、scope、版本兼容、冲突展示和排序；
7. `retention_policy`：事件/快照保留、脱敏和归档要求。

共享核心不得写 `if domain == ...`；根据注册表调用 adapter。adapter 不存在或版本不兼容时，明确标记 `unsupported_domain`/`schema_incompatible`，不应把它当作失败经验或用 finance 默认规则兜底。

### 13.4 可扩展领域示例及结果口径

| 领域 | 可沉淀的经验假设示例 | 可验证 outcome（示例） | 主要风险/特殊条件 |
|---|---|---|---|
| 金融/全市场选股 | 某市场状态 × 板块强度 × 量价/筹码组合 | T+1/T+3/T+5 净收益、基准超额、回撤、可成交率 | point-in-time、幸存者偏差、涨跌停、成本、复权、非平稳 |
| 软件工程/代码代理 | 某类仓库结构/错误特征下，某工具链或修复模式 | 定向测试通过、回归率、构建通过、修复时长、变更范围 | 测试覆盖不足、基线失败、代码版本/依赖差异、不能把“测试绿”当作无缺陷 |
| 数据分析/SQL | 某 schema/问题类型下的查询规划与校验策略 | 结果与参考集一致、约束通过、查询成本/延迟 | 数据快照变化、SQL 方言、参考答案不完备、权限边界 |
| 客服/流程运营 | 某类问题与上下文下的步骤/升级策略 | 用户问题解决、重复联系率、处理时长、人工升级 | 用户满意度偏差、政策版本、敏感信息、不同业务的损失权重 |
| 文档/知识问答 | 某类检索条件、来源组合或引用策略 | 引用支持率、答案正确性、时效性、拒答校准 | 知识库版本、引用可追溯、过期文档、评审集泄漏 |

领域 outcome 可以是实数、分类、集合一致性、时长、成本或人工复核结果；统一信封和 lineage，不强行压成一个跨域“胜率”。不同领域的效用若需做上层比较，必须先定义明确的业务效用函数和归一化版本。

### 13.5 建议的跨领域落地次序

1. **先建共享生命周期，不先追求万能 DSL。** 稳定 workstream、事件、版本、lineage、状态、evaluation manifest。
2. **金融域先闭环一条窄链。** 完成全市场候选/时点快照及 T+1/T+3/T+5 回放，解决 as-of 与候选覆盖；经验只做 shadow。
3. **并行验证一个非金融域。** 推荐先选软件工程，因为有版本化代码、可重复测试、清晰的 run/test 结果；先支持少量任务类型，不把测试结果等同于最终质量。
4. **比较两个 adapter 的公共需求。** 只有金融和代码两个不同时间/结果语义的 adapter 都能复用同一信封与生命周期，才抽象共享接口；不要根据单一 A 股域提前做过度通用化。
5. **再接其他领域。** 每接新域必须提交 domain schema、结果成熟策略、评估/数据质量政策、隐私与保留策略及离线 fixtures；完成影子评估后才开放检索注入。

跨领域扩展的判据不是“表里有 domain 字段”，而是新领域无需改共享表结构/核心编排即可注册 adapter，能独立验证自身结果、正确处理未成熟/不可判状态，并且不会被其他域的特征或权重污染。

### 13.6 增补验收门

- **点时性**：任一评估输入可证明在假设 `known_at` 时已可得；未来数据/修订数据注入测试必须失败。
- **关联完整性**：workstream 分叉/合并显式留痕；每个 hypothesis version 可重建输入证据和上一版本差异。
- **可复算**：同一 evaluation manifest 和固定数据版本重跑产生相同结果（允许定义好的数值容差）。
- **防过拟合**：保留候选尝试次数和研究者自由度；发布报告同时显示训练内、滚动验证与时间外表现。
- **域隔离**：没有 adapter、单位不兼容或特征版本不匹配的经验不得进入当前域线上候选。
- **容量**：按峰值日/年增长、索引、过期清理、归档恢复和回放查询做压测，并设可观测预算。
- **效果归因**：每项经验区分 eligible/exposed/applied/labeled；不可归因样本不强制分配，线上增量先 shadow 验证。
- **可回滚**：停用经验/adapter/统计政策不会删除证据或重写既有标签，且能恢复到上一个已知生效版本。

## 14. 关键边界：技能负责方法，经验负责动态条件与证据

> **补充来源**：用户指出“经验生成技能会过时，不生成技能又无法按个股当前状态检索；组合特征不可能全部写入技能”
> **补充时间**：2026-11-04 11:43（Asia/Shanghai）
> **性质**：对技能/经验职责及在线检索流程的增量澄清，不表示相关能力已实现

### 14.1 不是“生成 Skill”与“不生成 Skill”的二选一

矛盾来自把两种不同生命周期的知识都塞进 `SKILL.md`：

- **Skill 是相对稳定的分析程序**：说明要取哪些数据、如何核验、如何计算特征、如何检索经验、如何处理冲突/缺失、如何形成带时点的结论。它回答“怎么分析”。
- **Experience 是可更新、可过期、可回测的条件化证据**：描述“在何种可观测状态下，过去观察到什么结果、证据有多强、结论何时有效”。它回答“当前条件下有哪些经验可参考”。
- **当前决策输入是某一时点的事实快照**：包括标的、市场状态、消息/公告时点、价格量能及其他特征。它回答“现在处于什么状态”。

因此，不应把每个股票、每个日期或每种特征组合编译成一份新的 Skill。Skill 可以指导系统分析 000915，但不能写死“10 月 30 日前看空”或把一条历史经验无条件应用到今天。历史结论也不是因时间过去就自动变错：它只对原信息集和适用条件负责；今天是否可用，须重新检查当前条件、事件和时效。

### 14.2 000915 的两种分析时点

以两个独立的 point-in-time decision 为例：

1. **10 月 30 日前的回放**：只读取当时已知的业绩预期、价格、资金、板块和筹码等数据；生成 `decision_snapshot(as_of=t1)`，检索当时已存在且适用的经验。后来公告、下跌和增持消息都不能进入该次评估。
2. **今天的实时分析**：重新取当前数据和截至当前的消息，生成新的 `decision_snapshot(as_of=t2)`。事件到达后，旧快照不被改写；新快照可能显示市场状态、风险事件或筹码特征已变，因而旧经验不再适用，或者适用范围/证据需要新版本评估。

检索的对象不是“000915 专属技能”，而是与当前决策条件匹配的经验，例如：

- 同类业绩冲击后的价格/流动性状态；
- 筹码集中度或上方套牢盘变化；
- 个股相对板块强弱、市场风险状态；
- 增持公告的发布时间、可信度、规模及事件后价格反应；
- 目标 horizon、交易阶段和可成交性。

具体特征及其方向必须来自有定义、有来源、有时点的数据；像“上端筹码未松动”“18.5 附近抛压小”若无法由历史可复算数据支持，只能作为待验证输入或解释，不能由 LLM 当作既成事实。

### 14.3 高维组合不通过枚举解决

组合特征数量会随维度指数增长，不能把 MACD × 板块 × 资金 × 筹码 × 事件 × 波动率等所有笛卡尔组合逐条写入 Skill 或经验库。建议采用**可组合条件 + 有证据的交互 + 分层回退**：

1. 将原子特征按版本、单位、时间语义和来源登记；当前状态以紧凑 feature vector/snapshot 表示。
2. 经验条件引用有限的原子特征和明确的比较/窗口操作；不同经验可共享特征和关系，无需复制完整 Skill。
3. 先检索适用的总体/单条件经验；只有有样本量和预先定义的评估价值时，才检查少量高价值交互项。LLM 可提出候选交互，不可因文本上“看起来有关”就发布。
4. 使用层级回退：精确条件证据不足时，返回较宽的上层状态/单因素证据，并明确标记“弱匹配/证据不足”；不得把弱匹配伪装成精确经验。
5. 结果报告展示匹配条件、未匹配条件、证据样本与时间范围、冲突经验和缺失特征。不要只返回一个相似度分数或未经解释的结论。
6. 对尝试过的条件组合留研究记录，并用时间外样本、多重检验控制和最小效果门槛抑制筛选偏差。

这是“经验数据库按状态检索”而非“把所有状态预写成技能”。在统计样本足够时，可以使用经过版本化和校准的条件模型/分层模型来估计交互效果，但模型应作为可评估的经验对象，记录训练数据、特征口径、有效时间和评估结果；不可藏进不可审计的 prompt。

### 14.4 在线分析与检索流程

通用股票分析 Skill 应编排下列步骤，而不包含具体日期/股票结论：

1. 固定 `as_of`，获取当下分析必需的数据和事件，并记录数据新鲜度、源版本及缺失项。
2. 对输入特征做 schema/单位/时点校验；先处理公司行动、停牌、公告时点等会改变解释的事件。
3. 通过域、任务、市场/标的范围、horizon、时段及特征 schema 做硬过滤，再对条件签名/文本做候选召回；向量相似只能召回候选，不能决定适用性。
4. 用确定性条件 evaluator 逐条判断 `applicable / partially_applicable / not_applicable / unknown`，检查经验状态、有效期、数据版本和证据成熟度。
5. 取匹配经验及其支持/冲突/细化关系；按证据质量和适用性组织结果。遇到冲突先呈现差异条件，不由 LLM 擅自选一条。
6. Agent 结合实时数据、经验适用范围和反证形成分析；区分事实、统计证据、推断和不确定性，禁止将历史经验写成当前确定事实。
7. 记录检索曝光、实际引用、未采用理由、决策快照和最终分析，以便后续评估经验是否有增量价值。

若当前条件没有已验证经验，正确行为是按通用分析流程继续、明确说明“无直接匹配/证据不足”，而不是自动生成并使用一份新 Skill。新提炼的经验先进入候选/影子评估，只有满足对应门槛才进入检索候选。

### 14.5 时效性与失效判定

每条经验至少区分：

- `observed_at/known_at`：证据何时被观察/系统何时可知；
- `valid_from/valid_until` 或适用 regime：经验适用的时间/状态范围；
- `feature_schema_version` 与数据/模型版本；
- `freshness_policy`：哪些输入变化需要重新计算适用性；
- `evaluation_as_of`：评估数据截止点。

时间边界不能只靠固定 TTL。经验是否适用应主要由条件和 regime 决定；TTL 可用于标记需复核，不能替代状态匹配。新公告、财报、制度变化或特征口径升级可触发旧经验降级、暂停或待复核，但需保留旧版本和旧评估。对“今天”检索必须使用今天可得的数据重新评估适用性，不得直接复用旧 decision snapshot。

验收要求新增如下：

- 同一通用 Skill 在不同 `as_of` 下会针对不同快照检索，且不会将未来事件泄漏到历史分析；
- 组合空间扩大时，检索计算量受候选预算/条件白名单约束，不全量枚举特征笛卡尔积；
- 精确经验缺失或冲突时能明确降级/拒答，能追溯命中的条件和证据；
- 任何经验都不能绕过当前数据质量、时点、版本兼容及状态校验。

## 15. 个股异质性：同一经验在不同股票上可能方向相反

> **补充来源**：用户指出 A 股个股可能受不同主导资金/交易结构影响，同一经验在一只股票有效、在另一只股票相反
> **补充时间**：2026-11-04 11:51（Asia/Shanghai）
> **性质**：对经验适用范围、异质性检验和在线检索的增量补充，不表示相关能力已实现

### 15.1 这不必然表示经验错了

“MACD 金叉后更容易上涨”若被误写成无条件、全市场定律，在某些股票上方向相反，说明其**适用范围被过度泛化**，不一定说明所有观察都错。可能的解释包括：

- 股票流动性、持有人结构、筹码分布、波动和涨跌停特性不同；
- 个股所处的行业、市场状态或事件阶段不同；
- 资金行为/交易机制存在差异，但关键驱动不可直接观测；
- 特征、数据源或执行条件的口径不一致；
- 结果只是小样本噪声，或回测/样本选择偏差。

因此需要区分：经验在明确条件下的局部证据、可迁移的群体规律、尚不能解释的异质性，以及数据/评估错误。不能因为单个反例就删除局部经验，也不能因为少数股票有效就宣称全市场有效。

### 15.2 经验需要表达“适用对象层级”

经验的 `scope` 应支持从宽到窄的层级，例如：

`market/regime → sector/industry → liquidity/structure cohort → instrument → instrument × regime`

这不是要求每一层都建一条经验，更不是自动给每只股票生成专属规则。层级表示证据在哪些群体被验证，以及是否观察到稳定的组间差异。若发现股票间效果方向相反，应把假设拆成待验证的异质性问题，例如：

> 在特征 X 与状态 R 下，指标 Y 的效果是否随预先定义的流动性/持有人结构分组而改变？

先检验事前可解释、可复算的分组与交互，再决定是否建立更窄的适用范围。无法观测的“主力/庄家意图”不得直接作为特征事实；可用的代理变量必须注明来源、时点、测量误差和局限。统计相关不能证明某类资金操纵或因果关系。

### 15.3 分层估计，避免“一刀切”和个股过拟合

评估不能只给所有股票一个平均效果，也不能为每只股票独立拟合、独立发布规则。建议报告并比较：

1. 全市场/当前市场状态的基线效果；
2. 预先定义的行业、流动性、结构或事件组效果；
3. 个股偏离群体基线的方向与不确定区间；
4. 样本覆盖、有效独立事件数、时间外稳定性，以及组间差异是否超出噪声。

统计上可采用分层/部分汇聚：样本充分且稳定的个股允许显示更强的个体差异；样本稀少时向所属群体或全市场基线收缩，并标注低置信度。对个股专属信号设置更严格的样本和时间外门槛，使用滚动时间验证及跨股票验证，记录尝试过多少分组/交互以控制多重检验。分层模型是候选方法，最终仍须以可复算的离线评估和影子表现验收。

### 15.4 区分“互相矛盾”与“条件不同”

在线检索时，面对方向相反的经验，不应简单投票或按文本相似度取一条。系统应：

- 先比较双方的 `scope`、条件、市场状态、时点、特征口径和样本质量；
- 若适用范围不同，作为条件化结果并列返回；
- 若范围重叠且证据质量相近，标记 `conflicting_evidence`，展示分布与不确定性，不自动激活任一方向；
- 若一方只是少量个股/单次事件的候选观察，降为低置信度线索，不覆盖已验证群体基线；
- 若发现数据口径/时点错误，走数据质量纠错和评估新版本流程，不把它记成市场反例。

经验状态最好表达适用范围，而非用一个全局 `active` 标签代表普遍有效。可保留一条群体级经验，同时将其限制为“对该股票/状态不适用”或附加经验证的局部修正；每次范围调整必须产生新版本并保留旧证据。

### 15.5 主导资金/交易结构随时间变化

个股异质性不是永久属性。同一股票可能因股东结构、流通盘、流动性、事件或市场阶段变化而进入新的交易状态。因此：

- “股票代码”本身只能作为实体标识，不能替代可验证的状态特征；
- 对状态变更应按 `as_of` 重新计算特征，并记录变点/事件来源；旧快照和旧评估保持不可变；
- 分组定义、代理特征和变点检测器都要版本化，并评估误判；
- 出现结构变化证据时，将相关经验标记为需复核/适用范围待定，不能仅凭固定 TTL 永久作废或无限期沿用。

### 15.6 增补验收门

- 对显著异质性不能仅报告总体均值；至少检查预设分组及个股偏离，并提供样本量和不确定性。
- 个股专属效果需通过该股票的时间外验证；若要宣称可迁移，还需跨股票验证，二者不可混称。
- 对事后发现的分组/交互标注探索性，不能使用同一批数据既发现规则又宣称验证通过。
- 小样本的个股经验必须收缩/降置信或标记候选，不得覆盖群体基线。
- 线上冲突输出能指出究竟是 scope 不同、条件缺失、数据不可比还是证据真实相反；无法判断时明确保持未决。
- 所有涉及“主力/庄家/控盘”等解释均须区分可观测事实与推断，不得把推断伪装成已验证因果。

## 16. 一致性复核后的实施契约与易错点

> **补充来源**：用户要求复审全文并在无阻塞问题后继续细化方案、接口和易错点
> **补充时间**：2026-11-04 12:59（Asia/Shanghai）
> **性质**：一致性审查与逻辑接口草案；不是 API 已上线或数据库 migration

### 16.1 审查结论与需统一的语义

总体方向没有根本性冲突，但原文有若干容易被实现成互相矛盾行为的边界，以下规则作为全文的统一解释：

1. **经验生命周期、评估证据、单次适用性是三个正交维度，不能共用一个 status。**
   - `lifecycle_status`：`candidate → testing → shadow → active → suspended/retired`；`rejected` 为候选终态。`active` 仅表示经策略批准、可进入线上适用性检查，不表示所有股票/时点均适用。`expired` 不单独作为永久生命周期状态：有效期到达后按策略转 `suspended` 或 `retired`，并保留原因。
   - `evidence_status`：例如 `insufficient_data / evaluation_pending / supported / inconclusive / contradicted / invalidated`，由某个不可变 evaluation run 产生。新评估建立新记录，不覆盖旧结论。
   - `applicability_status`：每次决策独立计算 `applicable / partially_applicable / not_applicable / unknown / conflicting`，并记录匹配的 scope/条件、缺失项和 policy 版本。
   - `label_status`：单个结果样本的成熟/可判状态，如 `pending_maturity / labeled / undecidable / data_missing / infra_failure / not_applicable`。不能把它与经验发布状态混为一谈。
2. **点时语义必须区分“当时已知”和“后来提炼”。** 至少记录 `decision_as_of`、`evidence_as_of`、`candidate_created_at`、`evaluation_data_cutoff` 和 `effective_from`。若经验候选是在一段历史行情走完后才从案例总结出来，不能假装当时已经知道该经验：提炼后的候选可用过去数据做探索性研究，但其确认必须使用未参与提炼/选择的时间外数据；线上生效时间不得早于批准时间。历史决策回放只能读取该决策时点可得的数据和当时可用的经验版本。
3. **“经验不适用”不是“经验被证伪”。** 当前股票/状态不满足条件，只产生该 decision 的 `not_applicable`；只有经过符合预注册评估方案的数据，才可形成 `supported / contradicted / inconclusive` 等评估结论。个股异质性应作为 scope、交互和分层评估问题，而不是按单个反例直接改写全局经验。
4. **流程状态和适用范围不能互相代替。** 单一 instrument 的经验可在小范围候选研究，但不得仅凭该股票历史样本就成为泛化经验；其适用 scope 必须显式限定，单股/单事件证据和群体证据分开报告。新事件或 regime 变化可触发复核/暂停，不自动证明旧证据错误。
5. **全市场回测的 universe 也必须 point-in-time。** 不仅要记录 selector 实际产生的候选全集，还要冻结当时可投资标的集合/纳入规则、退市与停牌状态及过滤过程。若只保存最终候选或事后重建的幸存股票集合，不能据此声称已控制选择/幸存者偏差；无法重建时需把结论限制为已观测候选范围。
6. **append-only 指原始事实事件不可改写，不代表所有业务表都禁止更新。** 事件事实采用追加事件；当前状态、队列状态和聚合表可以是可重建的 projection/read model。审核撤销、状态转换、标签更正都追加新事件和新评估版本，旧事件/旧结果保留。现有可更新表迁移时须通过事件导出或版本化快照保留变更语义。
7. **“影子后激活”与“回测通过后激活”统一为串行门槛。** `candidate → testing` 完成离线评估，再进入 `shadow`（线上只记录匹配与反事实，不影响生产决策），通过影子期的数据质量/漂移/运行门槛后才可 `active`。任何门槛失败均保持或转为 `suspended`，不允许 LLM 直接改状态。极低风险流程性知识不属于可产生交易权重的经验发布路径。

### 16.2 建议的内部接口（逻辑契约，非 HTTP 路由）

所有核心接口应带 `contract_version`、`request_id`/幂等键，并返回显式状态；调用失败不得伪装成“无经验”。下面是职责/形状草案，实际命名可遵循仓库既有风格。

#### A. 决策快照构建

`build_decision_snapshot(request) -> SnapshotResult`

必需输入：`domain`、`task_type`、`subject`、`decision_as_of`、`horizon`、输入 source refs、feature schema versions、policy version。输出：不可变 `snapshot_id`、内容 hash、各 feature 的值/单位/source/as-of、缺失/质量状态、universe manifest ref（若适用）。

规则：

- `decision_as_of` 由调用链固定并向下传递，禁止各工具自行以“当前时间”替代。
- 数据发布时间、系统可见时间和业务生效时间分别记录；事件只有在当时已对系统可见才可作为决策输入。
- 同一 snapshot ID 对应不可变内容；修复源数据需产生新版本/hash，并保留旧引用。
- 关键特征缺失或过期时返回结构化质量状态，不以 0、空字符串或最新值静默填充。

#### B. 经验候选检索与确定性适用性判定

`retrieve_experiences(snapshot_id, policy_version, budget) -> RetrievalResult`

先按 domain/task/scope/horizon/lifecycle/effective interval/schema 过滤，再按索引/向量召回有限候选；每个候选必须经确定性 evaluator 检查条件。返回项至少含：

`experience_id/version_id`、`lifecycle_status`、最近 `evidence_status` 与 evaluation ref、`applicability_status`、matched/unmatched conditions、缺失/不兼容原因、scope 覆盖、样本量/时间外表现摘要、支持/冲突关系及排序理由。

适用性语义：

- 任何必需条件为 `unknown`，整体不可标成 `applicable`；三值逻辑中缺失不等于 false。
- `partially_applicable` 只用于明确允许部分条件匹配且结果仍可解释的情况，不能被下游当成完整命中；默认不改变决策分数。
- `shadow` 经验只能写曝光/模拟结果，不得影响线上排序；`active` 仍须逐次匹配。
- 若无候选，返回成功的 `no_match`；若数据库、特征服务或 evaluator 故障，返回可观测的 `degraded/error`，不能与 no-match 混淆。
- 经验优先级不是单一 embedding 相似度；首先保证 scope/schema/时点兼容，再考虑证据质量、覆盖程度、更新时间及冲突关系。

#### C. 曝光、应用和决策差异记录

`record_experience_exposure(event) -> event_id`

每条事件以唯一幂等键区分 `eligible`、`exposed`、`applied`、`not_applied`；记录 snapshot/decision/version/policy IDs、原因和时间。`applied` 需要引用真实的决策变化（如排序前后、分数差、文本引用区间）；没有可观测变化时只记 exposed，不推定产生贡献。工具、技能、市场经验沿用同一曝光信封，但 outcome 和聚合量纲分开。

#### D. 候选提炼与版本提交

`propose_experience(workstream_id, evidence_refs, extractor_manifest) -> candidate_version_id`

只接受可解析的 source refs、提炼时点和受限 DSL；生成的版本固定 `candidate_created_at` 与信息集边界。提交后由 validator 检查特征注册、类型/单位、时间可得性、scope、关系环及重复候选；校验失败返回逐字段错误，不写入可检索候选。人工/LLM 修订都产生新版本，不能原地覆盖。

#### E. 异步评估与发布

`submit_evaluation(version_id, evaluation_manifest, idempotency_key) -> evaluation_run_id`

manifest 固定数据快照/universe、特征版本、交易日历、horizon、成交/成本模型、基准、分层、时间切分、试验登记号及统计政策版本。提交返回 `queued/running/completed/failed` 等任务状态；结果保存输入 manifest hash、输出 hash、各分层指标、样本覆盖、排除原因和运行器版本。重跑相同 manifest 必须幂等或显式标识新 run。

`transition_lifecycle(version_id, target_status, approval, gate_results) -> transition_id`

仅允许合法状态转换；`shadow → active` 必须引用已通过的离线 run、影子期报告、数据质量/漂移门槛和审核主体。失败时说明具体 gate，不得只返回 false 或自动放宽门槛。暂停/撤回不删除既有证据。

#### F. 领域 adapter 最小契约

领域 adapter 负责提供类型和语义，不把领域判断散落到共享服务的 `if domain == ...` 分支中。最小能力包括：

- `validate_snapshot`：特征、单位、时间与数据质量；
- `validate_condition` / `evaluate_condition`：DSL 静态校验与三值求值；
- `build_universe_manifest`（适用的任务才实现）：历史时点可重建的标的/对象全集；
- `resolve_outcome` / `maturity_status`：结果观测、标签成熟和不可判原因；
- `evaluation_policy`：指标、基准、时间切分、成本和发布门槛；
- `retrieval_policy`：scope 兼容、证据排序、冲突呈现；
- `retention_policy`：数据保留、脱敏和归档。

没有 adapter 或 adapter 版本不兼容时，明确返回 `unsupported_domain` / `schema_incompatible`；不使用 finance 默认 resolver，也不把这种错误标成负面 outcome。

### 16.3 DSL 与数据模型的实施边界

首版 DSL 采用白名单 AST，不允许任意 SQL、Python、正则回调或模型生成代码。一个条件节点必须包含稳定的 `feature_key`、`feature_schema_version`、operator、类型正确的 value/unit、窗口/时段语义和缺失策略。示意：

```json
{
  "all": [
    {
      "feature": "market.sector_relative_strength_5d",
      "schema_version": 2,
      "op": "gte",
      "value": 0.0,
      "unit": "percent"
    }
  ]
}
```

该示例只表示语法形状，不代表已选定特征定义或策略阈值。首版限定比较、集合包含、布尔组合和有限窗口算子；限制 AST 深度、节点数、时间窗口和计算预算。`null` 默认传播为 `unknown`；如要使用 `is_missing` 等显式判断，必须作为单独 operator 并纳入评估，不能把缺失值隐式当成某个区间。

数据库实施时需特别处理：

- PostgreSQL 分区表的唯一/主键约束通常必须包含分区键；若 `event_id` 要求全局唯一，需采用全局 ID 注册表/非分区主表，或将分区键纳入幂等键设计，不能假设分区表可直接提供全局唯一约束。
- 追加事件的幂等键要包含事件类型与来源版本，避免重试重复写入，也避免不同事件误冲突；projection 更新需可从事件重建。
- 逻辑外键、分区归档与删除策略要在 PostgreSQL 16 的真实 migration 中验证，不能仅凭逻辑表图假定所有跨分区外键均可用。
- 大对象快照的 URI 不足以保证重放；需同时保存 content hash、schema、source version、as-of、保留期限和可访问性状态。
- JSONB 仅用于小型、版本化 payload；常用于筛选/连接的域、状态、特征版本、时间和实体标识应有明确列/索引。先测实际查询，再决定 GIN/BRIN/分区。

### 16.4 关键易错点与必须覆盖的测试

1. **信息泄漏**：把后来总结的经验倒灌到总结所依据的历史样本；用公告发布日期代替实际可见时间；使用修订后的历史行情/幸存者 universe。测试需构造未来信息并确保历史检索/评估拒绝它。
2. **标签时间偏移**：T+1 的交易日历、买入可成交时点、除权除息和涨跌停处理不一致。对每个 horizon 明确起算点、价格口径、无成交处理、跨节假日和午休规则。
3. **重复计样本**：同一股票同日由多个 run 重复出现、重叠持有期或 worker 重试导致样本被多次计权。定义独立样本单位（事件/股票/决策日）和聚类/权重规则，并做幂等重跑测试。
4. **把相关当因果**：经验命中后结果好，不证明经验导致改善；工具/技能共同曝光也不能平均分功。无随机化、可信对照或反事实识别时只报告条件关联。
5. **反例和冲突处理**：单股失败不自动否定市场级经验；总体有效不覆盖有稳定证据的相反子群。重叠 scope 需显示冲突与不确定性，禁止隐式按“最新版本”覆盖。
6. **选择偏差和未覆盖对象**：只评估 agent 挑出的股票会形成截断样本；全市场 universe 必须是当时可投资总体且可重建。只能保存边界候选时，报告必须声明估计对象受限。
7. **小样本与多重尝试**：搜索很多特征组合后只报告胜出的规则，会严重高估效果。保存全部尝试、筛选和实验政策；发现集与确认集分离，单股/单事件经验提高发布门槛。
8. **数据故障冒充无经验**：DB 超时、resolver 缺失、schema 不兼容和真正 no-match 必须可区分并监控；主对话是否 fail-open 由调用面策略决定，但审计结果不得静默成功。
9. **活跃版本缓存过期**：缓存键必须包含 snapshot/as-of、policy、经验版本与 feature schema；激活/暂停后有失效机制，且不可跨用户/任务污染上下文。
10. **成本和可用性**：LLM 提炼、向量召回和回测均异步/有预算；线上只进行有界候选召回和确定性求值，超时返回显式部分结果/服务降级状态，不能无限扩展搜索。
11. **隐私与提示注入**：对多轮原文、工具输出和用户数据做最小化留存/脱敏；引用内容视为数据而非指令，LLM 候选须能回链原证据并通过 schema/权限校验。
12. **回滚不是删除**：撤销发布只改变当前可检索版本和追加状态事件，不删除历史决策、曝光、evaluation 或旧经验版本；复现历史结果必须按当时的发布快照读取。

### 16.5 MVP 接口/数据实施顺序

为避免先铺全量表与万能 DSL，建议把前两个可交付里程碑收敛为：

**MVP-A：只读经验检索与评估 manifest**

- 建立 feature registry、不可变 decision snapshot、有限条件 AST、评估 manifest/hash；
- 接一个 finance adapter，先对少量可复算特征实现确定性匹配；
- 对既有历史数据只做 as-of 能力/Universe 覆盖审计，不满足就明确限制可回答的问题；
- 检索只产出证据卡片，不改变排序、不生成交易权重；为每次结果保留 trace 与 no-match/error 区分。

**MVP-B：曝光漏斗与影子运行**

- 记录 eligible/exposed/applied/not_applied 事件及稳定幂等键；
- 按预注册的少数经验版本运行离线和在线影子评估；
- 验证分层/个股异质性报告、冲突显示、性能预算、归档重放和停用回滚；
- 通过真实数据质量、统计门槛与人工审核后，再决定是否开放 `active` 经验对线上决策的影响。

在 MVP-A/B 之前，不建议批量生成每股 Skill、不建议用 LLM 相似度直接激活经验、不建议同时迁移旧权重表并改变交易排序。

## 17. 经验分类、优先级与排序：需要，但不使用单一总分

> **补充来源**：用户询问经验是否需要打分/权重/排序/分类以增加辨识度和优先级；参考 `del/agent模块四维审计报告_20261101_原文备份_20261103.md` 中现有权重口径审计
> **补充时间**：2026-11-04 13:08（Asia/Shanghai）
> **性质**：检索排序与经验治理规则补充，不表示当前权重链已完成统一或经验已用于交易排序

### 17.1 结论：分类与排序必需，评分分层使用

经验库需要分类和优先级，否则检索结果会把稳定流程、局部市场观察、低样本候选和已被反证的经验混在一起。但不应把所有属性压成一个 `weight`：

- **检索相关度**：这条经验与当前任务/状态有多匹配；
- **证据强度**：经验的评估结果是否稳定、可复算、样本是否充分；
- **适用性**：当前快照是否满足它的 scope 和条件；
- **经验生命周期**：它是否允许被线上检索/影子观察；
- **决策影响权重**：若允许影响分数/排序，影响幅度是多少；
- **运行/安全优先级**：例如数据质量、风险约束等必须先于策略经验执行的硬规则。

这些维度不可互相替代。高文本相似不代表证据强，高证据不代表适用于当前股票，`active` 不代表应给它较大的交易权重。MVP 阶段优先使用**硬门控 + 分层/字典序排序**；不先设计一个看似精确但无法校准的综合分。

### 17.2 分类字段建议

分类应采用可组合的受控标签，而非单选一个含义混杂的类别：

| 维度 | 示例 | 用途 |
|---|---|---|
| `knowledge_type` | `data_contract`、`process_rule`、`empirical_pattern`、`exception/counterexample`、`tool_behavior`、`risk_constraint` | 决定 evaluator、可否回测及消费方式 |
| `domain/task_type` | finance/stock-selection、finance/single-stock-analysis、code/bug-fix 等 | 域隔离和任务召回 |
| `scope_level` | market/regime、sector/cohort、instrument、instrument×regime | 明确群体或个股适用范围 |
| `time_horizon/regime` | T+1/T+3/T+5、盘中/盘后、事件阶段 | 避免跨周期误用 |
| `evidence_grade` | `E0` 未评估、`E1` 探索性、`E2` 时间外验证、`E3` 多窗口/多群体验证、`E_invalid` 数据或方法失效 | 显示证据成熟度；具体门槛由领域 policy 定义 |
| `lifecycle_status` | candidate/testing/shadow/active/suspended/retired/rejected | 控制发布与可见性 |
| `applicability_status` | applicable/partial/not_applicable/unknown/conflicting | 当前一次决策的适用性，不是经验固有属性 |
| `risk/priority_class` | `hard_constraint`、`high`、`normal`、`exploratory` | 决定处理顺序；不得覆盖域安全门槛 |

`E0–E3` 是展示层级，不可跨领域直接比较。比如股票回测与代码修复的“E2”须分别由各自 adapter 的 evaluation policy 解释。反例/例外应作为一等知识类型保留，可限定某些 scope 或触发冲突复核，不应直接被压成负分。

### 17.3 两段式排序

**第一段：硬门控（不参与打分）**

剔除或隔离：域/任务不匹配、时间点不合法、schema/单位不兼容、生命周期禁止消费、数据质量不合格、明确不适用、证据已失效。任何硬门控失败都不能被高相似度或高历史收益“加分抵消”。

**第二段：同一可比组内排序**

先按可解释层级排列：

1. 硬性安全/数据契约（先执行；不与收益经验比较）；
2. 当前 `applicable`、scope 最贴合且证据已通过该领域门槛的 active 经验；
3. applicable 但证据较弱/局部的经验，作为带标签的参考，不自动改变决策；
4. shadow/testing/candidate，仅供评估/诊断，不作为生产建议依据；
5. partially applicable、conflicting、unknown 和反例单独分组展示，不混入正向命中列表。

在同一层内按以下顺序作稳定排序：条件匹配与 scope 精确度 → 时间外证据/跨样本稳定性 → 有效样本量与不确定区间 → 数据质量/可复算性 → regime/版本兼容及复核状态 → 近似召回分数。新旧程度仅用于时效复核和同等证据下的 tie-break，不能无条件让最新经验胜出；同一 scope 有相反结果时必须并列标 `conflicting` 并展示差异，不允许排序把冲突隐藏。

可在同层排序后显示若干**分项指标**（例如匹配覆盖、有效样本量、时间外增量及区间、数据质量、最后复核时间），但不默认合成一个 `priority_score`。若未来确需综合分，只能在同一 domain/task/outcome/policy 内用历史曝光与人工标注校准；需版本化、可解释、做离线/影子验证，并提供分项回退。跨域、跨 outcome、跨 scope 的总分不可比较。

### 17.4 检索优先级不等于交易权重

`retrieval_rank` 只决定先向 agent 展示哪些证据；它本身不能直接调高股票 rank、BUY 置信度、仓位或经验“可信度”。要让经验影响生产决策，必须另有显式的、领域定义的 `decision_effect`/策略组合器，说明影响对象、方向、上限、风险约束、冲突策略和回滚方式，并通过影子/对照评估。

分项记录建议至少包括：

- `retrieval_policy_version`、排序依据与候选预算；
- `applicability_status`、命中/未命中条件及 scope；
- `evidence_grade`、最近 evaluation ID、样本量/独立样本定义、时间外指标与不确定区间；
- `decision_effect_policy_version`（若没有则明确 `none`）；
- `exposure/applied` 事件与真实决策差异。

### 17.5 权重口径的特别警告

随附四维审计报告指出，现有 skill、factor、tool、chain 权重的统计口径和样本门槛并不统一（例如收益/时间收益与胜率混用）。因此：

- 不得拿现有某层的权重直接作为经验库排序分或跨层优先级；
- 不得把 tool reliability、skill outcome、市场经验有效性合成同一个权重；
- 在迁移/统一权重前，先逐项标注 metric、标签来源、样本单位、窗口、样本门槛和缺失策略；
- 权重缺失/样本不足应表现为 `unknown/insufficient_evidence`，不能静默回填 0、1 或中性后伪装成已评估。

这与第 5 节一致：可以共享事件和证据基础，但 typed aggregate、量纲、读取用途和校准政策必须分开。

### 17.6 易错点与验收

- 同一条经验的分类、证据等级、生命周期和本次适用性分别存储；不得由一个 `priority` 字段代替。
- 安全/数据硬约束优先级不能被经验分数覆盖；候选经验和 shadow 经验不得影响线上排序。
- 不适用不扣证据分，未成熟不算负面，缺数据不等于条件不成立。
- 个股经验不得因“scope 精确”就排在群体经验之前；排序还要展示样本量、不确定性和跨股票可迁移性。
- 新近经验不能自动覆盖历史证据；冲突经验必须被显式呈现。
- 排序结果须可追溯到 policy 版本、分项依据及被硬过滤的原因；相同输入和版本应产生稳定结果。
- 第一版验收应测排序稳定性、门控正确性、冲突可见性、影子无决策影响及不同领域指标隔离；暂不以收益提升作为检索排序的单独验收代理。

## 18. 待检验分层假设：流通市值与经验稳定性

> **补充来源**：用户提出“股票流通市值和经验稳定性成正比”
> **补充时间**：2026-11-04 13:21（Asia/Shanghai）
> **性质**：研究假设，不是已验证结论

### 18.1 将直觉转为可证伪命题

可将该观点表达为：

> 在预先定义的经验、市场状态和评估口径下，决策时点的流通市值越大，某经验效果在不同时间段/股票样本间的波动越小，或其方向一致性越高。

这里“稳定性”必须明确是**经验效果的可重复性**，而不是股票价格更稳定、经验平均收益更高、胜率更高或更容易成交。应至少分别报告：

- 效果方向在滚动时间窗/时间外窗口的保持率；
- 不同股票/预设股票组间效果的异质性（如组间方差或异质性区间）；
- 经验效果估计的不确定区间及有效独立样本量；
- 对收益分布、回撤、成交率和成本敏感性的稳定程度。

这些指标不得揉成一个“稳定分”而不展示分项。命题不预设线性正比；可以是阈值、分段或非单调关系，需由样本验证。

### 18.2 可能机制与反向因素

较大的流通市值可能对应更深流动性、更高机构参与或更低的单一资金影响，从而减小部分短期噪声；但这只是可能机制，并非流通市值本身的因果证明。反向或混杂因素包括行业/指数权重、国企属性、股东结构、成交额与换手、波动率、涨跌停/停牌、事件冲击以及不同市值股票的策略适用性。大市值股票也可能出现风格切换或拥挤交易，小市值股票的某些事件型经验则可能在严格限定状态下有稳定局部效果。

因此，市值只能作为一个候选分层特征，不能直接成为经验可信度的乘数，也不能据此预先降低小市值股票经验的优先级。

### 18.3 评估要求

1. 使用每个决策时点可得的**流通市值**（自由流通股数 × 当时价格，注明复权/公司行动口径），不能用今天的市值回填历史；并记录源、as-of 和特征版本。
2. 事先固定经验集合、horizon、结果指标、滚动/时间外切分、样本单位和市值分组方式；避免反复切桶后只报告最显著结果。
3. 同时检验原始分层关系及控制关键混杂后的稳健性，例如行业、流动性/成交额、换手、波动、市场状态和事件类别。控制变量是诊断，不自动证明因果。
4. 按股票和时间进行适当分组/聚类，避免同一股票相邻交易日或重叠持有窗口被误算为大量独立证据；报告每组覆盖股票数、独立事件数和置信区间。
5. 采用滚动时间外与跨股票验证，检查关系是否跨时期、跨行业和不同经验类型复现；探索性分组与确认性评估分开。
6. 同时检查经验“方向稳定”与“经济价值”——即使方向稳定，也可能收益很小、成本后消失或无法成交；不能把稳定性直接当作可交易性。

### 18.4 系统使用规则

在证据不足阶段，流通市值可用于检索过滤后的结果分层展示和研究报告，不参与经验 `evidence_grade`、`retrieval_rank` 或交易决策权重。若后续多期/多股票时间外验证支持其调节作用，应把它作为显式、版本化的 scope/条件或分层模型特征；仍需保留大小市值组的分项证据与不确定性，不能简单地“大市值经验可信、小市值经验不可信”。

验收时应包含反例测试：若控制混杂后关系消失、方向反转，或仅在某一时期/行业成立，系统需保留相应局部范围并报告未复现，不得继续输出全市场“成正比”的结论。

### 19.1 总体结论：复用 C3P，经验库不是第二套预测/权重引擎

AGENT_DESIGN_v3 的核心原则与本方案可兼容：LLM 负责从分析中抽取可引用、可证伪的条件证据；确定性代码负责点时校验、概率校准和结果评估；冻结的 `p_base` 与经验修正分开记录。现有 `chain/c3p.py`、`evidence.py`、`aggregator.py`、`calib_feed.py`、`calibration.py`、`context_frame.py` 已有对应接线。

因此，首期不另建一条与 C3P 竞争的“LLM 生成经验 → 直接打分/改权重”流水线，也不把所有经验编译为 Skills。应把系统拆成三个清晰面：

1. **案例记忆（CBR）**：`utils/case_memory.py` 的文本相似案例，作为少量流程参考/复盘素材；不能当成结构化、已验证的条件经验，也不能直接修改概率。
2. **条件化预测证据（C3P）**：按标的、方向、horizon、点时快照登记预测；经验只在适用条件和统计门槛满足时修正对应基线预测。
3. **技能（Skill）**：稳定的分析步骤、工具选择、数据质量与输出规范；不存股票/日期专属结论，不承载统计系数。

统一事件/证据 lineage，但不合并它们的标签、分数和消费口。

### 19.2 首期范围与明确排除项

**首期 A 股 MVP 范围**

- 主体：数据契约可确认的 A 股普通个股；以股票代码为 subject，按当前可运行的行情与基线预测范围进一步收窄。交易所/板块、ST、停牌、退市及新股等边界按现存数据源和模型的真实覆盖列出，不从通用“全 A”字样推定支持。
- 任务：单只股票的方向性预测和经验证据检索；输入必须有可解析股票 subject、固定决策时点和明确方向/horizon。
- 结果：先以 `predict_next_day` 的 T+1 上涨概率为唯一校准主口径。T+3/T+5 可以继续形成独立 claim/result 和离线报告，但在相同 horizon 的独立 baseline 与 point-in-time 标签口径就绪前，不得用于 T+1 概率校准。
- 条件：首轮只用已验证的市场 regime、波动档等低维情境键；少数可复算的个股特征先登记为候选，不一次扩成大量交互格。以独立簇预算为准，不能因名义案例多就扩格。
- 输出：呈现当前适用的已验证证据、范围、样本/独立簇、时间外表现和不确定性；第一阶段只读/影子，不影响生产排序、仓位或 BUY/SELL 决策。

**首期不承诺**

- 全市场选股的 rank/portfolio alpha。`sampler.pick_daily_universe()` 的 hot/warm/cold 配额抽样用于情境覆盖和校准采样，不等于保存了 selector 的完整 point-in-time investable universe，也不能证明全市场排序效果。
- 指数、行业/板块 claim 的方向校准；C3P 的 `resolve_subject()` 只接受 `subject_kind == "stock"`，不能把个股基线外推给指数/板块。
- ETF、可转债、期货、期权、港美股、分钟级策略、盘中撮合、基本面长期预测，或未经确认的所有 A 股边界。
- 任何“主力/庄家意图”作为直接可校准特征；只有定义清晰、历史可复算的代理变量可作为候选。

全市场选股是第二条独立验收线：需另有 point-in-time universe、候选全集/过滤理由、ranker 冻结版本和可成交组合回测；不能把单股 C3P 通过当作市场选股能力已验证。

### 19.4 代码核对发现：进入任何预测修正前的阻断项

以下是对当前代码路径的静态核对，不是生产数据成功率或真实预测效果评估。

1. **多空 claim 与 `p_base` 结果含义可能错配。**
   - `app/watchlist/predict.py::predict_next_day()` 输出的是 `p_up`（次日上涨概率）。
   - `calib_feed.build_samples()` 将 claim resolution 的 `VERDICT_SCORE`（该 claim 是否命中）与 `p_base` 均值用于条件格拟合。
   - 对 bearish claim，直接把 `p_up` 当成“该 bearish claim 为真”的基线概率会反向错配；`magnitude`、`level` claim 的命中率也不能用 `p_up` 校准。
   - **实施要求**：首期正式校准只接 `claim_type=direction`，明确定义方向概率映射（bullish 使用 `p_up`；bearish 若语义严格是“下跌”则需经 outcome contract 核准后使用互补概率；neutral/模糊/幅度/价位 claim 不进入该校准）。先用真实 claim fixture 验证 resolution 标签与预测目标完全同义；未核准前该类样本只记账、不拟合。不能仅靠 `verdict_score` 的 0/0.5/1 认为标签可直接作为概率真值。
2. **一条 evidence 被复用于多条 claim。**
   - `c3p.run_for_decision()` 目前以 `works[0]` 调一次 `extract_evidence()`，随后在 `works` 循环中复用同一 `ev` 和 condition key；多只股票或不同方向/claim 的情况会把第一条的判别/证伪证据套到其他 claim 上。
   - **实施要求**：按 claim 单独生成/关联 EvidenceVector；只有同一 subject、同一 information set 且证据确实共享时才能显式共享，并用共享引用而不是隐式复用。每条 pair 必须绑定自己的 `claim_id`、subject、horizon、snapshot、condition key 和 evidence version。
3. **历史 as-of 缺帧会回退到最新情境。**
   - `c3p.current_frame(as_of)` 在找不到指定日期时返回 `frames[-1]`；这会把未来情境带入历史评估。
   - `qd_aftercare._c3p_pipeline()` 当前调用 `run_for_decision()` 时没有透传 `as_of`。
   - **实施要求**：as-of 必须由决策源传入；请求历史日期但缺少对应帧时返回 `missing_snapshot/unknown` 并禁止正式校准，不能回退 latest；实时“最新”行为也要显式指定为 live mode。
4. **C3P 接线不等于学到了 LLM 经验。**
   - 当前 `calib_feed._fit_all()` 输出以 `b0` 为主，按 `condition_key` 校准基线偏差；`aggregator` 虽有 discriminator/falsifier 系数入口，但现有 feed 未提供经样本拟合的特征系数。
   - **实施要求**：将当前能力标为“情境条件基线校准”，不能称为“特征经验已学习”。只有在可复算 feature exposure、独立训练/确认数据、适用方向/标签正确及样本预算通过后，才可新增 feature β 或交互项。
5. **经验强度、证据来源类别和发布状态语义混杂。**
   - v3 要求 `evidence_class={live,rule,replay}` 表示污染/证据来源；代码 `evidence._evidence_class()` 返回 `{weak,medium,strong}` 表示内容完整度。
   - **实施要求**：两个字段分开命名与存储（例如 `source_class` 与 `evidence_completeness`）；不得在 migration/报表中以一个字段互相覆盖。
6. **`Δp` 符号检验不足以单独证明预测变好。**
   - `sign(Δp)` 与方向标签一致性可以回答修正方向是否合拍，但不保证 `p_final` 比 `p_base` 概率校准更好，也不代表交易成本后收益改善。
   - **实施要求**：保留 v3 预注册的符号/斜率诊断，同时在适配明确 outcome 后报告同一样本上的 paired proper scoring（如 Brier/log loss 差及聚类不确定区间）；交易表现另由独立策略回测评估。不得把三个问题混成一个胜率。

以上 1–3 属于 MVP 进入正式拟合前必须修复并有测试的口径/时点问题；4–6 属于避免夸大能力和保证评估有效的阻断性契约。

### 19.6 需要后续补充的数据可行性，但不是可以跳过的准确性门槛

用户提出数据源可以后续增加和细化，这可用于**扩展范围**：首期只接少量已确认可用的数据，之后再加入公告、股东/筹码、流通市值、行业成分、实时资金等特征。

但对任何被纳入首期评估或线上匹配的 feature，仍必须先通过最小数据可行性门：来源可识别、单位和计算口径固定、决策时点可证明、缺失/修订可区分、可在样本期重放或明确标为仅前向积累。不能先用当前值/最新值做回测，再把数据问题留到未来修补；历史不可重建的 C 类特征从上线采集日开始积累，积累期间只能 shadow/描述，不能宣称已有历史验证。

特别是流通市值与经验稳定性的命题：v3 首期条件格预算不支持随意增加市值×regime×vol 等笛卡尔组合。先把决策时点流通市值作为分层诊断变量，报告组间覆盖/异质性；只有样本功效与预注册方案允许时才作为正式条件或部分池化变量，不直接加权经验可信度。

### 19.7 进入编码前的决策清单

以下工程决定可按本规格默认收敛，不需再等待“全市场所有数据齐备”；需在 migration/写代码前以离线审计数据确认：

1. 首期是否严格限定为普通 A 股单股方向预测；当前 `p_base` 只支持 T+1，因此 T+3/T+5 是否先只做独立 outcome 报告。
2. 哪些现存证券代码/板块/特殊状态在 `predict_next_day` 和行情数据源中有可验证覆盖；无法确认者列为 `unsupported`。
3. 方向 claim 的真值、涨跌死区、T+1 起算价/可成交假设是否与冻结 `p_base` 的训练标签一致；若不一致先重建对应 baseline 或暂停该校准。
4. C3P 的 pair/evidence/context frame 过渡文件与 DB 的唯一真源/迁移窗口；不得长期双读双写而无对账。
5. A 股全市场筛选何时启动第二个独立 workstream；启动前先提供历史 point-in-time investable universe 与完整 selector candidate/funnel。

完成上述清单并修复 19.4 的阻断项后，方案可进入首期编码；在此之前可做 A0 数据与代码审计、接口类型/fixture 准备，但不应开放经验对生产交易建议的影响。

## 20. 修订首期覆盖范围：A 股全任务面，多 horizon 并行评估

> **补充来源**：用户澄清首期要覆盖金融领域的整体任务面，必须包含全市场选股和板块选股；T+1/T+3/T+5 是并行评估窗口，不应被视为互斥选项
> **补充时间**：2026-11-04 22:10（Asia/Shanghai）
> **修订关系**：本节覆盖并修订第 19.2 节“首期范围”中将 MVP 限定为单股方向/T+1 的表述，以及第 19.7 节中将全市场选股留作后续第二 workstream 的排期。第 19.4 的代码问题仍是待解决的工程阻断项，但不得据此缩减产品目标。

### 20.1 范围裁定

首期目标是 **A 股主要股票分析与选股任务的统一经验闭环**，而不是单一的单股方向预测：

- 单只股票分析/方向、价位或风险判断；
- 全市场选股与候选排序；
- 行业/板块强弱判断、板块内选股与跨板块比较；
- 与上述任务直接相关的市场状态、组合结果与风险评估。

ETF、可转债可在后续作为新的 instrument/task adapter 单独纳入；期货、期权、港美股及分钟级交易暂不纳入首期承诺。首期“覆盖整体任务面”不等于立即支持所有证券品种、所有特征和任意策略；每个任务须在支持矩阵中标明数据/标签/评估是否已就绪，不支持的组合显式返回 `unsupported` 或 `data_insufficient`，不得静默套用个股预测器。

第 19 节中列出的代码边界仍须修复，但产品范围改为以上三类主要任务并行建设；可以按里程碑分批开放能力，不能把尚未开发的 task evaluator 解释成不属于首期目标。

### 20.2 T+1/T+3/T+5 是同一决策的并行 outcome

T+1、T+3、T+5 不是相互排斥的预测类型。一个决策可以绑定同一 `decision_snapshot`，在多个 horizon 分别生成 outcome：

`decision_id + subject + task_type + horizon + outcome_metric + evaluation_policy_version`

每个 horizon 独立记录成熟状态、可成交假设、标签和评估结果；T+1 已成熟时可以先评估，不必等待 T+3/T+5。未成熟窗口保持 `pending_maturity`，不得以较短窗口结果冒充较长窗口结果。T+N 中 N 按交易日计算，且必须固定决策 cutoff、交易日历版本、起算规则和数据可见时间。

按用户举例，若 2026-11-04 已收盘且该日行情可用：

- 2026-10-30（周五）收盘后的决策，11-02 为 T+1、11-03 为 T+2、11-04 为 T+3，因此 T+3 可成熟；
- 2026-10-28（周三）收盘后的决策，10-29 为 T+1、10-30 为 T+2、11-02 为 T+3、11-03 为 T+4、11-04 为 T+5，因此 T+5 可成熟。

若当日尚未到评估数据截止时点，或行情源尚未完成落库，应仍标记未成熟/数据未就绪。对每个 horizon 生成独立 outcome，而不是把 `T+1/T+3/T+5` 做成三份互不关联的经验或三套互相覆盖的生命周期。

数据库不建议把每个 horizon 扩成一组重复列（如 `t1_return/t3_return/t5_return`），宜将结果保存为带 `horizon`、`metric_id`、`status`、`value` 和 `evaluation_run_id` 的 outcome 子记录；常用字段可物化/索引，但必须有唯一键和单位契约。这样后续增加 T+10、T+20 或分钟窗口不需反复改主表。

### 20.3 不同任务共用经验平台，不共用结果定义

共享 `decision_snapshot / evidence / experience_version / exposure / evaluation_manifest / lineage` 等基础契约；每种 task 使用明确的 task-specific evaluator 和 outcome schema。

| 任务类型 | 评估对象 | 必要结果口径（各 T+N 分开） | 不能用什么替代 |
|---|---|---|---|
| 单股分析 | 一个 subject 在某时点的一项可验证判断 | 方向、目标/支撑/风险等分别定义可判 outcome；方向概率须有同 horizon 的概率基线 | 不能用“整段回答对/错”代替多条 claim |
| 全市场选股 | 一个时点的完整可投资 universe、selector 候选与排序 | Top-K/分位组合的净收益、基准超额、回撤、换手、覆盖率、可成交率；按 T+1/T+3/T+5 独立结算 | 不能只评 agent 最终推荐的几只票，也不能把单股 `p_up` 当排序质量 |
| 板块选择/轮动 | 同一时点所有符合定义的行业/板块及排名/入选集合 | 板块相对基准收益、排名相关/Top-K 命中与组合指标；按 horizon 独立结算 | 不能拿单只股票胜率或个股上涨概率替代板块选择效果 |
| 板块内选股 | 先冻结板块集合，再评估其成分股筛选/排序 | 同时评估板块选择误差与板块内选股结果，并保留两阶段归因 | 不能把板块选错与选股选错混为一个经验标签 |

任务结果标签可以相关，但统计单位和 estimand 不同。系统可共享原始事实、候选和事件 lineage，不得把单股 hit、板块 hit、Top-K 净值及工具正确率折成同一 `win_rate` 或权重。

### 20.4 全市场选股的最低数据与决策契约

全市场 selection run 必须以“完整决策对象”而非个股 claim 为根：

- 冻结 `decision_as_of`、市场阶段、策略/ranker/过滤器版本、特征 schema、价格复权和成本政策；
- 保存当时可投资 universe 的定义/成员 manifest（包括退市、停牌、上市天数、ST 等过滤状态及规则版本）；不可重建时必须把评估范围限制为可观测子集；
- 保存 selector 输入候选、过滤后候选、最终 rank/score、被排除原因、Top-K 和决策边界附近对象；需能识别未入选对象，避免只对成功推荐标的打标签；
- 若完整逐股快照成本过高，可存不可变 universe/source manifest、数据版本与 hash，另存完整排序输出和边界样本；任何抽样都记录概率/规则并在估计时校正，不能静默抽样后仍称全市场指标；
- T+N 评估应同时提供理论结果与交易模拟，明确可成交时点、涨跌停、停牌、滑点、费用、容量和组合再平衡方法；
- 一次策略组合的收益样本单位是 `selection_run/portfolio × horizon`，不是把组合中的每只股票当作相互独立策略样本。统计不确定性按交易日、组合形成批次及重叠持有窗口聚类/修正。

`sampler.py` 的 hot/warm/cold 分层配额仍可作为**覆盖率/情境采集**机制，但其抽样清单不能替代 selector 的完整 universe、排序 funnel 或无偏全市场回测。

### 20.5 多 horizon 概率校准与当前 C3P 的边界

同一套经验库可以评估多个 horizon，但概率校准必须满足预测目标与标签严格同口径：

1. `p_base`、经验修正、`y` 必须匹配相同的方向事件、horizon、决策时间和可成交/价格定义。
2. 现有 `predict_next_day` 只提供 T+1 `p_up`；它不能直接作为 T+3/T+5 的概率 baseline。T+3/T+5 可先独立做回测 outcome，若要概率校准，需各自建立并冻结对应 horizon baseline，或采用另有契约的非概率排序 estimand。
3. bearish claim 的标签需和“下跌概率”目标一致；neutral、区间/幅度、止损/价位触达、盈利/亏损 claim 不可直接复用同一 `p_up` 及 hit 评分系数。
4. 对全市场/板块选股，主评估应是排序/组合指标；若另外输出概率，只能作为另一项 outcome，不得用单股概率校准结果宣称 selector 已优化。
5. 各 horizon 独立保留 `label_status` 和 evaluation run。多重测试按预注册的 task×horizon×outcome 家族控制；不能把 T+1、T+3、T+5 当成三次互不相关、可任挑最佳的一次性显著性测试。

这样既满足多个 horizon 的实际需要，也保留第 19.4 的阻断原则：现有多空 claim 与 `p_base`、逐 claim evidence 复用和历史 frame latest 回退问题仍要先修，不能通过“多加 horizon 字段”掩盖。

### 20.6 更新后的交付顺序：广任务目标，窄切片验收

采用**架构与 schema 按多任务设计，按可验证的纵向切片逐步交付**，而不是把产品范围缩成单股方向：

**M0：A 股任务/数据覆盖盘点**

**M1：共同决策/快照/outcome 契约**

**M2：三条只读/离线纵向切片**

三条切片共享数据/经验版本底座，但各有 task evaluator、指标和发布政策；先分别对账历史基线和人工可复核样例，再进入影子。

**M3：跨任务经验检索与影子**

**M4：受控生产消费与扩展**

这一裁定不要求在第一天同时上线所有功能；要求从一开始按正确的多任务、多 horizon 实体关系建模，避免先把数据库和 API 锁死为“一个股票 + 一个 T+1 概率”，以后再做高风险迁移。

## 21. 架构原则修订：整体升级现有经验与权重闭环，不预设保留 C3P

> **补充来源**：用户明确本次目标是整体升级现有“只能简单整体分析个股”的经验库和工具权重；允许为灵活性、适用范围、智能和预测效果重构 C3P、经验及闭环链路，借鉴现有实现，也允许移除冗余链路。
> **补充时间**：2026-11-04 22:24（Asia/Shanghai）
> **修订关系**：本节修订第 19.1 节“复用 C3P，经验库不是第二套预测/权重引擎”的架构结论，以及第 19.5 节中默认以现有 C3P 为中心的交付措辞。第 19.4 节对当前代码行为的核查仍是有效事实和风险清单，但不再意味着必须保留当前 C3P 结构。第 20 节定义的 A 股任务范围和多 horizon 目标继续有效。

### 21.1 目标不是给旧经验库旁边再叠一套

本次升级的对象是现有经验库、工具权重、技能反馈、C3P/校准和结果评估组成的**整体学习闭环**。不得把增加新表、新服务或新检索器本身当成升级完成，也不得仅为兼容旧实现而保留功能重复、口径冲突或无法证明价值的链路。

目标系统应支持：从单轮和多轮运行形成有时点与出处的经验候选；面向不同任务、主体、市场范围和 horizon 检索适用证据；把适用性、不确定性、冲突证据和工具/技能效果用于可追溯决策；通过点时回放、影子和结果评估更新经验；在效果退化时限制、降级或撤回。提智不是增加 LLM 自由裁决权，而是让系统更准确地辨认“什么经验、在什么条件、对什么任务和时点有用”，并用结果证明增量价值。

因此，本文先前的“统一证据基础，但保留 CBR、C3P、Skill 与工具权重为相邻独立面”只能作为当前代码盘点的描述，不能作为最终架构约束。最终可采用统一的逻辑闭环和存储/服务边界；确需区分的部分应是有明确契约的 evaluator、evidence type 或 read model，而不是互相竞争、重复采集和分别更新的多条经验真源。

### 21.2 目标闭环：一个事实与生命周期，多个有类型评估器

建议将主链路统一为以下可追溯过程：

1. **决策上下文冻结**：记录 task、subject/universe、决策 cutoff、当时可见数据与来源、策略/模型/工具/特征版本；多轮问题通过明确的 thread/workstream 关联，但每次判断保留自己的信息时点。
2. **运行与证据归集**：把 LLM 主张、工具观察、特征快照、用户纠正、技能/工具曝光和中间判断关联到该决策；事实、推断、假设、缺失和冲突不得混为一类。
3. **经验候选生成与版本管理**：LLM 可从单轮或多轮过程提议经验拆分、合并、条件化或失效；候选保留来源和父子关系，不能自行变为有效经验。重复、矛盾和仅由一次结果支持的候选需进入去重/审核/验证流程。
4. **统一检索与适用性判定**：先按任务、horizon、时点、主体范围、数据/特征兼容性及生命周期做硬过滤，再做条件匹配、局部证据与群体先验的分层汇总；`unknown`、数据缺失、过期和冲突必须显式呈现，不能当作匹配成功。
5. **决策消费与曝光记账**：消费者读取按类型定义的证据/效应，不直接读取任意一个“万能经验分”；记录被检索、符合条件、实际展示/应用、贡献方向和未采用原因，并支持影子反事实比较。
6. **成熟结果与归因评估**：按决策绑定各自的 task × horizon × outcome evaluator；单股概率校准、全市场排序/组合、板块选择、工具可靠性、技能效果分别使用合适 estimand，但共享决策 lineage、曝光、数据快照和评估运行管理。
7. **受控更新与回滚**：由确定性评估和发布政策更新对应的经验状态或类型化效应估计；版本化、可限幅、可降级、可撤回。历史决策读取当时的经验发布快照，不受后续更新改写。

“一个闭环”指共享身份、时点、证据来源、经验版本、曝光和结果追踪，不代表把不同目标强行压成一个指标。一个市场经验的收益表现不能证明工具正确；工具成功率也不能证明选股有效。区分评估器是目标异质性所需，不构成重复经验引擎。

### 21.3 现有链路按功能评估，不按名称保留

对 `case_memory`、C3P/EV-1、`qd_agent_weights`、`qd_skill_feedback`、技能选择事件、工具调用记录及现有 aftercare/评估流程，逐项核对：输入/输出语义、事实来源、样本单位、as-of 保证、结果标签、更新规则、真实读写消费者、线上影响和可回放性。之后按下表决策：

| 现有能力 | 目标处置原则 |
|---|---|
| C3P 的 claim/evidence 配对、点时快照、基线与条件效应分离等有效能力 | 若契约正确且覆盖目标任务，可抽取后纳入统一决策/证据闭环；不要求保留当前模块边界或表结构 |
| C3P 当前的单一 T+1 `p_up` 校准、低维情境截距或 stock-only 限制 | 视为当前实现能力，不是最终经验模型；按任务×horizon×outcome 重新定义接口和评估器，未经同口径验证不得泛化 |
| `case_memory` 文本相似案例 | 可作为统一经验候选/证据的来源或检索解释，不保留一套与结构化经验平行、且会被误认为已验证结论的独立反馈生命周期 |
| `qd_agent_weights`、工具/技能反馈及其他权重表 | 盘点其实际消费者后迁入同一证据与曝光闭环；仅在需要时保留按类型计算的只读聚合/兼容视图，不让多个表独立更新同一效应 |
| Skills 中稳定、可复用的流程纪律 | 保留为执行规范或能力说明；股票/日期/状态相关的可检验经验转为带版本、条件和评估结果的经验对象，不复制生成大量动态 Skill |
| 重复的提取、校准、aftercare 写入、标签或 ranking 路径 | 若语义和职责重复，选定唯一权威路径后合并或退役；保留期间必须有明确迁移期限、对账和删除条件 |

该处置是功能级而非仓库文件级的预判：在完成实际写入/消费盘点前，不直接删除代码或表。发现无消费者、无有效标签或重复写入的历史数据时，也先确定其审计与迁移需求，再安排退役。

### 21.4 C3P 的定位：可借鉴的组件，不是不可变的总架构

C3P 现有代码中的优点和已发现缺陷都应纳入升级评审。`claim → evidence → prediction pair → resolution → calibration` 可作为一个历史实现样本；可以重构为统一经验闭环里的预测/条件效应评估器，也可以在证明维护成本或能力不足时整体替换。是否复用由契约正确性、可扩展性、可回放性、复杂度和实测增量决定，而非由已有代码投入决定。

保留或重写后的任何条件化预测模块至少必须做到：

- 输入和输出显式绑定 task、subject/universe、方向或排序目标、horizon、决策时点、标签定义和 evaluator 版本；
- 基线、条件证据、经验修正和最终输出分开记录，能重算每一步的来源和贡献；
- 不把单一方向概率校准套用于价位、幅度、风险、排序或组合目标；不同 estimand 只能通过显式适配器转换，且各自验证；
- 缺少点时快照、标签口径不符、证据不匹配或历史数据不可重放时，返回可诊断的 unsupported/data_insufficient 状态，而非以最新数据、默认概率或成功形状回退；
- 经验交互复杂度受预算和预注册控制；未验证的候选只可影子评估，不能因 LLM 生成或检索相似而获得决策权限。

第 19.4 节列出的多 claim evidence 复用、历史 frame 回退、方向/标签错配等问题仍须在盘点和纵向验证中处理：若复用对应路径，则修复并测试；若替换，则证明新路径不存在同类错误，并迁移/隔离受影响历史样本。它们是必须解决的风险，不是要求照搬 C3P 的实现任务清单。

### 21.5 统一经验与工具权重，但保留类型化语义

工具权重不再作为与经验升级并行的独立优化项目，也不把旧工具权重简单并入市场经验总分。每类反馈先定义“可观察事件 → 可验证结果 → 估计对象 → 允许消费位置”：

- 工具：调用成功/失败、返回数据正确性/新鲜度/覆盖度、延迟成本，以及在特定 task/context 下对决策证据或结果的增量；
- 技能：版本在特定任务下的流程完成质量、证据覆盖和下游结果；
- 市场经验：条件命中、对应 outcome 的时间外增量及不确定性；
- 编排策略：工具/技能组合对质量、成本和时延的联合影响。

上述结果共享曝光和决策 lineage，但分别估计、分别设样本门槛和消费权限。单次工具调用成功不代表对决策有帮助；被选择调用的工具也存在选择偏差。多工具共同贡献且不能识别时应标记不可归因，而非平均分配收益。权重应是满足相应验证门槛后的类型化效应估计或可靠性参数，必须有适用范围、置信/样本信息、限幅和失效机制；不允许无条件全局排名、跨任务迁移或绕过仓位/交易风险 guard。

旧表/消费者只有在新闭环的回放与影子对账通过后才能切换。迁移期可为兼容而生成只读旧格式，但不允许旧链和新链同时独立更新同一权重；明确切换点、回滚窗口、差异阈值与退役条件。

### 21.6 实施路线与架构验收

1. **盘点现状**：只读追踪各链路的生产者、存储、消费者、状态转移和真实线上影响；标出重复数据、断链、无消费结果、无法回放及隐式默认值。结论以调用/数据证据为准，不因模块名判断功能。
2. **冻结统一契约**：定义 decision/thread、point-in-time snapshot、typed evidence/experience、exposure、task-specific outcome、evaluation manifest、发布快照及错误状态；先覆盖第 20 节所有任务和 T+1/T+3/T+5 的实体关系。
3. **选代表纵向切片**：单股、全市场选股、板块选择各至少一条；同时覆盖多轮假设变化、工具使用/未使用、条件不适用、缺数据和相互冲突经验。比较新旧链路的可重放结果和成本。
4. **统一事实源与读侧**：完成可幂等迁移和新旧对账后，指定单一写入/生命周期权威；兼容视图限期保留。重复链路逐项合并、禁写、迁移或退役。
5. **只读/影子验证再发布**：先验证无泄漏、适用性判定、预测/排序增量、工具/技能反馈归因、性能容量和故障语义；有证据的 task slice 才逐项开放，失败可降级回中性/基线并可回滚。

**完成标准**：不仅是文档或新表落地，而是每项在线经验/权重都能回答其来源、适用范围、当时可见信息、评估样本、相对基线增量、不确定性、使用记录、当前发布版本和撤回方式；不同任务不串用标签；多轮信息不倒灌历史；重复链路有明确退出结果；新链路在时间外/影子对照中相对现状有可量化价值，或明确证明暂不应影响决策。

### 22.1 定位：通用 Agent 底座 + 可验证的专业领域学习层

本项目的目标可表述为：**借鉴 Hermes Agent 的通用型、可持续学习 Agent 思路，为量化投资构建带点时数据、结构化经验、统计验证与交易结果闭环的专业领域升级版。**

```text
通用 Agent 能力

                 ↓

                 ↓
经验学习闭环
决策快照 → 证据与经验候选 → 条件检索/适用性判断 → 任务决策

```

领域升级的关键不是让通用 Agent “更会说股票”，而是让它能提出可检验的经验、在正确时点检索适用证据、识别异质性和未知状态，并通过可重放的任务结果逐步改善。通用 Agent 的会话记忆和 Skills 是重要输入/执行层，但不能替代专业证据和评估层。

### 22.2 借鉴点及专业化改造

### 22.3 经验、记忆与 Skill 的三分边界

为获得 Hermes 式的持续学习能力，同时避免把未经验证的语言总结误作交易规律，写入与检索需要区分三类对象：

1. **对话/运行记忆（episodic）**：保存发生过什么、谁提供了信息、做过哪些判断与操作，支持跨会话检索和追溯；它是经验发现素材，不直接代表有效规律。
2. **专业经验（empirical）**：表达在明确条件、主体范围和信息时点下可被数据反驳的假设；拥有版本、适用性、证据量、独立样本、结果指标、置信区间和状态；只有经验证的版本可以按发布政策被决策层读取。
3. **Skill/程序性知识（procedural）**：表达如何完成稳定的分析流程、调用工具、处理缺失/冲突并输出结果；可以引用经验检索接口，但不能复制易变的股票状态、经验系数或“当前有效”的市场结论。

LLM 可在这些对象之间提出转换建议（例如多轮会话 → 候选经验，反复修正 → Skill 流程缺口，过期条件 → 经验版本更新），每次转换都保留来源链接和审核/评估状态。检索结果必须标识“历史案例”“候选假设”“已验证经验”“流程 Skill”等类型，不能只返回一段合并后的记忆摘要。

### 22.4 相对通用 Hermes Agent 的专业能力增量

专业版应明确补足通用会话 Agent 通常不承担的能力：

- **点时正确性**：所有用于历史经验匹配、提取和评估的数据均需证明决策当时可见，考虑公告发布时间、行情修订、复权、交易日历和延迟。
- **多任务与多尺度**：支持单股判断、全市场候选排序、板块选择/板块内选股；每项可绑定 T+1/T+3/T+5 等独立 outcome，禁止跨任务/窗口借用分数。
- **候选全集和反事实**：全市场任务留存 universe、入选/排除和完整排序证据，评估策略与经验的增量，而非只复盘最后推荐且幸存的股票。
- **统计与市场异质性**：区分相关/因果、名义样本/有效独立簇、局部有效/群体可迁移；控制多重检验、重叠窗口、幸存者偏差、选择偏差和成本。
- **线上权限治理**：候选生成、检索展示、影子影响和生产消费分级；能力、置信度、证据来源、风险限制与发布状态不可混成一个可任意放大的“Agent 自我评价分”。
- **回滚与审计**：任何自动总结、经验激活、权重更新或 Skill 改动均可追溯、对比、撤销；后台自我改进不得悄悄改变生产决策。

### 22.5 不照搬的做法与验收方式

- 不把“模型觉得值得记住”当作经验有效；由 LLM 决定记忆优先级时，仍需可解释的留存/冲突/过期策略。
- 不在使用过程中让交易相关 Skill 无审查地自我改写并立即生效；改动生成新版本，经过回归、影子及相应发布 gate。
- 不把对话检索命中、工具调用次数、Agent 自评、子代理共识或单次收益当成经验权重。
- 不以 Hermes 通用能力的存在证明金融预测有效；专业效果必须和冻结基线在相同 PIT 数据、相同 task/horizon 和预注册指标下比较。
- 不为追求“自进化”而增加持续运行、子代理或新服务；只有在完整链路能降低遗漏/时延/成本且不削弱可审计性时才纳入。

**验收问题**：系统能否从多轮运行中准确提取候选，同时不把过程记忆误认为规律；能否在当前决策时点检索到适用经验并识别失效/未知；能否让经验、工具或流程改变产生可重放的增量对照；能否在发现退化时停止影响决策。四项均需有独立测试和可观测结果，才可称为专业领域的持续学习闭环。

## 23. 量化与经验协同：同一决策引擎的两类互补信息

> **补充来源**：用户强调量化和经验应并行发挥作用，但不能冲突或相互矛盾。
> **补充时间**：2026-11-04 22:42（Asia/Shanghai）
> **修订关系**：本节澄清第 21 节“基线与经验效应可分解记录”以及第 22 节“记忆/经验/Skill 分层”的含义：分层是为了可追溯和正确评估，不代表量化与经验形成两套互相竞争的决策链。

### 23.1 统一定位

量化与经验不是两个各自输出买卖结论、最后再由 LLM 二选一的系统：

- **量化**提供可计算、可复现的市场状态、特征、基线预测、排序与风险约束，并给出适用范围和不确定性；
- **经验**沉淀历史上在特定条件下被观察、解释和验证过的模式，包括结构化统计经验、事件/情境经验及从多轮分析中提取的候选知识；
- **统一决策**把当前量化证据与当前可适用的经验作为同一决策上下文的输入，判断条件是否成立、证据是否独立、两者是否已经重复表达同一信息，再输出一个带来源分解和不确定性的结果。

经验不是量化的对立面：通过历史结果验证的经验，本身就是对量化关系的条件化表达；量化模型则为经验提供检验、比较和校准的方法。自然语言经验可以补充尚未进入特征体系的事件脉络或交互假设，但在获得结构化定义和足够证据前，只能作为待验证的上下文，不得伪装成统计信号。

### 23.2 单一推理路径，不是两套分数相加

统一决策流程按以下顺序工作：

1. 冻结相同的决策时点、数据快照、task、subject/universe 与 outcome/horizon。
2. 生成量化基线和当前状态描述；记录特征、模型版本、校准状态及风险限制。
3. 检索适用经验，确定其条件命中、证据强度、局部适用范围、时效和独立样本；区分已验证经验与候选叙述。
4. 检查经验与量化模型是否使用同一来源/同一特征，避免把同一证据重复计权；判断经验是补充信息、已被模型吸收的信息，还是明确的交互/分层条件。
5. 由该 task 对应的受控组合器形成一次统一输出。组合方式可为模型特征/交互项、经验证的条件校准、分层先验或排序约束；只能采用在对应 task×horizon×outcome 上通过验证的方式，不预设统一线性加分。
6. 同时记录量化基线、经验候选及其贡献、融合结果、被排除/未采用原因和不确定性；线上输出不是多个相互矛盾的结论集合。
7. 将成熟结果反馈到同一 decision lineage，分别评估量化基线、经验信息以及二者联合后的增量，支持继续融合、降权、限域或停用。

这保留了“基线/经验效应/最终结果可分解”的审计要求，但基线不是与经验竞争的最终答案，经验也不能绕过量化验证直接覆盖基线。组件分离是为辨认增量贡献，不是产品层面的两条腿各走各的。

### 23.3 冲突时的处理原则

当量化基线与经验候选方向不同，系统不得静默选择任一方或简单投票。依次检查：

- **时点一致性**：两者是否使用同一 `as_of` 信息集，经验依据是否已经过期或包含未来信息；
- **定义一致性**：task、主体范围、方向、horizon、价格/成交口径是否相同；
- **适用性**：经验条件是否实际满足，缺失/未知特征是否被错误当成满足；
- **证据独立性**：经验是否只是对模型已使用特征的文字重述，或者来自相同样本的重复统计；
- **范围异质性**：是否存在经验证的局部条件，使总体量化关系在此情境下反转或变弱；
- **稳健性与风险**：冲突是否跨时间外样本复现，成本后是否仍有价值，是否触及硬风险限制。

处理结果按证据状态确定：

| 状态 | 决策行为 |
|---|---|
| 口径/时点不一致、数据缺失或条件未知 | 不融合该经验；输出基线及明确的数据/口径限制，不把冲突解释为经验有效 |
| 经验只是已入模信息的重复描述 | 不重复加权；可用于解释基线，但记录为零新增信息 |
| 经验为候选或样本不足，且与量化基线冲突 | 保持量化基线及风险控制，不让候选改变排序/方向；将其送入影子/后续验证 |
| 经验证的局部经验在同任务、同 horizon、同口径下稳定提供增量 | 由对应融合器在该局部 scope 内调整预测/排序，并保留基线与调整量；不可外推到其他股票/任务 |
| 两者均有较强证据但冲突未能解释或稳定解决 | 提高不确定性、降低决策置信/排序优先级，必要时 abstain；不得制造确定性结论 |
| 经验触犯合规、数据质量或硬风险规则 | 风险/合规 guard 优先；任何经验和模型输出都不能绕过 guard |

LLM 可解释冲突并提出需要补充的证据，但不能自行决定统计权重、改写量化输出或把“叙事更合理”当成胜出条件。若系统当前无法可靠融合，应明确标记冲突并减少结论强度，而不是宣称二者已经互补。

### 23.4 统一评估“量化单独、经验单独、联合增益”

每个 task×horizon×outcome 的评估都应在同一冻结样本和相同可交易假设下至少比较：

1. 量化基线；
2. 量化基线 + 经检索的经验；
3. 经验/条件信息的可识别增量（仅在其目标与标签相匹配时报告）；
4. 必要时的无经验消融、经验置换/随机对照或分层对照。

指标使用任务对应的 proper scoring、排序/组合、风险和成本后结果，并以预注册的时间外验证和适当聚类不确定区间判断增益。不得以“经验解释得更好”、训练集拟合提升、单次案例命中或工具调用更多来替代联合增益验证。若经验单独不强但能稳定改善基线，可作为条件增量保留；若无增量或造成退化，应停止其决策影响但保留历史记录和研究价值。

### 23.5 架构与验收约束

- 只设一个权威的决策输入快照、经验发布快照和最终决策记录；量化证据与经验证据是其中带类型的来源，不维护互相覆盖的平行结论。
- 量化模型、经验候选/版本、融合器和风险 guard 分别版本化；一个决策固定记录其组合关系，确保可回放。
- 经验的生命周期与量化模型生命周期相互关联但不互相冒充：新模型可能吸收旧经验；模型更新后必须重新检查经验的增量价值，不能假设旧经验仍带来额外信息。
- 工具/技能效果用于改善证据采集和分析流程；其权重不直接等价于市场预测系数。工具提供的数据通过统一快照进入同一决策，而非另加一个工具“投票分”。
- 生产消费只接受通过对应验证的联合组合器；降级时回到清楚标记的基线/保守策略，而不是退回到一套未经校验的经验打分。

**验收标准**：同一输入下只有一个最终 task 输出；能明确指出量化基线是什么、哪些经验适用、它们是否提供独立增量、冲突如何处理、融合改变了什么以及证据有多强；按 task×horizon 的时间外对照证明联合效果不劣于基线且达到预设增量/风险门槛，否则经验保持只读或影子状态。

### 24.1 实施边界及首期交付

首期实现的是**统一决策经验闭环的只读与影子版本**，覆盖四种任务类别：

| `task_type` | 决策对象 | 首期评估器 | 结果与成熟窗口 |
|---|---|---|---|
| `stock_analysis` | 单只 A 股的方向、价位、幅度或风险 claim | claim 类型对应的 evaluator；不支持的 claim 类型显式跳过概率校准 | 每条可判 claim 及 T+1/T+3/T+5 独立 outcome |
| `market_selection` | 某时点完整可投资 A 股 universe 的选择/排序 | Top-K/分位排序及组合 evaluator | T+1/T+3/T+5 净收益、基准超额、风险、换手和成交约束 |
| `sector_selection` | 同时点可比较的行业/板块集合及排序 | 板块相对表现与排名 evaluator | T+1/T+3/T+5 板块相对表现/排名及组合指标 |
| `sector_stock_selection` | 冻结所选板块及其成分股后的二阶段选择 | 分别评估板块选择和板块内排序 | T+1/T+3/T+5，保留两阶段归因 |

首期的“覆盖”指契约与流水线可表达、能标记支持状态；并不承诺所有任务×horizon 都已经有足够的 point-in-time 数据或可信基线。每个组合状态只能是 `supported`、`shadow_only`、`forward_collection_only`、`data_insufficient` 或 `unsupported`，并记录原因；禁止以单股 T+1 `p_up` 代替全市场/板块排序基线。

第一阶段不允许经验改变生产方向、排序、仓位或下单；先完成只读检索、历史回放和影子比较。所有新表/读侧启用由显式 feature flag 控制，默认关闭生产影响。

### 24.2 唯一核心对象与 ID/时间约定

统一使用不可变的 `decision_id`（UUID）作为经验、曝光和结果的核心归因键。现有 `qd_agent_decisions.id`、`qd_agent_traces.id`、`qd_agent_cases.case_id`、claim/resolution ID 均作为 `legacy_ref`，不得互相替代或通过“同股票、同一天”近似关联。

核心实体约定：

- **Decision**：一次在冻结信息集上的可复现任务决策。一次对话 run 可无决策（闲聊等）、有一个决策，或有多个不同 task/subject 的决策；不可把 run、跨轮 workstream 与决策快照混为一个 ID。
- **Decision snapshot**：`decision_as_of`（含时区）、`information_cutoff`、交易日历版本、市场阶段、特征 schema/数据 source snapshot、基线/排序器版本、策略/代码版本及其内容摘要。历史回放必须读取该快照版本，不读取“当前最新”。
- **Subject/universe**：个股、板块或全市场 universe 用类型化 key 表示；selection 保存 universe 定义与 point-in-time 成员/来源 manifest，不能用股票代码字段装入逗号列表。
- **Horizon**：数据库存储整数 `horizon_trading_days`，显示层可映射成 `T+1/T+3/T+5`；绑定日历版本、cutoff 和起算规则。分钟窗口使用单独的 `horizon_unit`，首期不启用分钟 evaluator。
- **Outcome**：由 `(decision_id, outcome_key, horizon_trading_days, evaluator_version)` 标识；例如方向概率、Top-K 净收益、板块排序质量是不同 outcome。一个 decision 可有多个 horizon 和多个 metric。
- **Feature provenance**：每个用于条件判断的特征带 `feature_key + schema_version + value/status + source_id + known_at + observed_at`；原始高频数据只存引用、hash、频率和时间范围，不复制进经验表。
- **经验版本**：`experience_id` 标识假设家族，`experience_version_id` 标识不可变版本；改 scope、DSL、目标 outcome、特征定义或效应估计均创建新版本。

所有时间以 UTC `TIMESTAMPTZ` 存储，并另外保留交易所本地业务日期；数据库不可仅存无时区 `DATE/TIMESTAMP` 来判定决策可见性。数据特征的 `known_at <= information_cutoff` 是经验适用和历史评估的硬条件。

### 24.4 DSL、候选生成与检索接口

经验条件使用受限、可版本化 DSL；首期允许表达式：

```json
{
  "schema_version": "condition-v1",
  "all": [
    {"feature": "sector_relative_strength_5d", "feature_version": "v2",
     "op": "gte", "value": 0.02},
    {"feature": "turnover_rate", "feature_version": "v1",
     "op": "between", "value": [0.01, 0.08]}
  ]
}
```

允许操作符仅为 `eq/ne/gt/gte/lt/lte/in/between/exists`，布尔节点仅 `all/any/not`；禁止 SQL、Python、模板执行、任意函数、任意网络或文件访问。阈值单位和缺失规则由 feature registry 定义；未登记特征拒绝进入可执行候选。`unknown` 不等于 `false`，只要条件无法判定，Applicability 返回 `unknown` 而不是部分命中。

内部服务接口首版固定如下（具体类型以 Python dataclass/TypedDict 落地，接口错误不通过 `None` 混淆）：

```python
record_decision(snapshot: DecisionSnapshot) -> Result[DecisionRef, WriteError]
record_exposure(event: ExposureEvent) -> Result[ExposureRef, WriteError]
propose_experiences(source: ExperienceSource) -> list[ExperienceDraft]
validate_experience(draft: ExperienceDraft, registry: FeatureRegistry) -> ValidationReport
retrieve_experiences(query: RetrievalQuery) -> RetrievalResult
evaluate_conditions(version: ExperienceVersion, snapshot: DecisionSnapshot) -> Applicability
build_decision_evidence(snapshot: DecisionSnapshot) -> DecisionEvidence
evaluate_outcomes(manifest: EvaluationManifest) -> EvaluationReport
publish_experience(version_id: UUID, report_id: UUID, policy: PublishPolicy) -> PublishResult
```

关键返回状态：

- `RetrievalResult.status`: `ok`、`no_match`、`data_insufficient`、`unsupported`、`stale_snapshot`、`store_unavailable`；
- `Applicability.status`: `applicable`、`not_applicable`、`unknown`、`conflict`、`stale`；
- `Outcome.status`: `pending_maturity`、`ready`、`scored`、`data_missing`、`unresolvable`、`invalid_contract`；
- `EvaluationRun.status`: `queued`、`running`、`complete`、`insufficient_data`、`invalid_input`、`failed`；
- 写入失败可以作为旁路不阻断用户回答，但必须保留可观测错误与重试 id；禁止将 DB error 伪装成 `no_match` 或空成功结果。

检索固定顺序：task/domain/instrument/horizon/outcome/schema/lifecycle/as-of 硬过滤 → 有界索引召回 → DSL 确定性执行 → scope 适配与局部/群体关系 → 冲突聚合 → 证据排序。文本 embedding 只扩大候选召回，不改变适用性和有效状态。返回结果需含候选版本、过滤/命中/未知条件、证据报告、独立样本与时间外切分、同源证据组、冲突关系和检索 policy version。

### 24.5 决策融合、量化/经验去重与发布 gate

决策输入拆为可重放的 `baseline`、`current_features`、`experience_evidence`、`fusion_policy`、`risk_guard`。冻结基线可以由当前量化 predictor/ranker 提供；经验作用只能通过对应 task×horizon×outcome 的已验证融合策略影响输出：

- 在模型尚无可检验联合效应时，经验只能作只读解释或 shadow 特征，不加权、不改排序；
- 若经验与基线特征同源，标记 `redundant_with_baseline`，不可重复计权；如明确建交互项，必须用时间外对照证明交互增量；
- 对局部反向关系，优先把条件化效应作为模型中有约束的分层/交互项估计，避免在线检索后简单叠加一笔经验分；
- 多条经验有重叠或矛盾时，按共享样本/特征来源聚类并联合评估，不把高度相关经验当独立投票；
- 保留来源贡献分解，但每次只产出一个 final 输出；冲突未解决时提高不确定性或 abstain，硬风险 guard 始终优先。

生命周期事件状态集合：`proposed → needs_data | validating → shadow → active → degraded | withdrawn | expired`；`rejected` 为验证/审核终态，可由新版本重新提出。不得 `proposed → active`。生产激活必须同时满足：DSL/特征质量通过、任务口径一致、独立验证样本达到该 task policy 要求、时间外联合增量达到预注册门槛、风险/成本不恶化、线上 shadow 稳定、审批和发布快照完成。具体门槛在 A0 的样本功效与业务成本审计后固化在版本化 policy 文件；不得在结果出来后调低门槛。未达到即停留在 `shadow` 或 `needs_data`，不应以虚构默认数值制造“可上线”表象。

### 24.6 评估器契约（首期四类）

所有 evaluator 实现同一协议：输入冻结的 `EvaluationManifest`；输出每个 task×horizon×metric 的样本纳入/排除数、成熟率、主指标、置信区间/聚类方法、数据质量警告、基线/联合差异和可重跑 hash。不得自行读取 latest 数据或猜测 horizon。

| Evaluator | 纳入单位 | 主报告 | 必须的控制 |
|---|---|---|---|
| 单股方向/claim | claim × subject × decision × horizon；概率比较只纳入目标标签严格同义且有同 horizon 概率 baseline 的 direction claims | Brier/log loss、校准和方向诊断；交易 claim 另报告成本后结果 | 每条 claim 单独证据/概率配对；同一 claim 多次 resolution 只按 manifest 规定的唯一成熟版本计一次；neutral/level/range/magnitude 不混入方向校准 |
| 全市场选股 | decision/portfolio × horizon | Top-K/分位净收益、基准超额、回撤、换手、成交率、容量/成本敏感性 | 冻结 PIT universe、完整候选与排除原因；按日期/重叠持有期聚类；样本不能把同一组合的股票当独立策略 |
| 板块选择 | decision × eligible sector set × horizon | 相对基准收益、排名相关、Top-K 与组合指标 | 冻结板块集合与成分版本；行业变化和不可比板块单独处理 |
| 板块内选股 | decision × 已冻结板块集合 × horizon | 分别报告板块选择、板块内排序和端到端组合效果 | 两阶段决策分别留痕；不得仅以总组合结果给某个阶段经验归因 |

T+1/T+3/T+5 分别落 outcome 子记录；任一窗口未成熟不阻塞其他窗口。交易日成熟计算统一委派项目唯一交易日历/label 真源；标签源缺行情、停牌、涨跌停不可成交、退市等要区分 `data_missing`、`untradeable`、`delisted`、`matured`，不可统一当 miss。

### 24.7 对旧链路的具体迁移与退役判据

1. **`qd_agent_decisions/claims/resolutions`**：保留成熟的追责数据；增加对 canonical decision 的显式映射。禁止 C3P 按位置把一个 EvidenceVector 复用于多 claim。新链须逐条 claim 生成/关联证据或明确 evidence group；历史样本无法确定 claim 归属时排除校准并打 `legacy_ambiguous`。
2. **C3P/JSONL pairs/evidence/calibration file**：先停止把它当唯一权威训练源，保留只读导入适配器；对历史文件做版本、hash、重复键和 resolution 关联报告。新 decision/exposure/outcome 写 DB 后进行 shadow parity。DB 侧来源、对账和回滚 gate 通过后，停止旧 JSONL 新写；旧文件按审计保留，不双写无限期。
3. **`qd_agent_cases`**：继续存 run 级情节记忆；不再用 `pending/correct` 作为所有经验生命周期。已有相似检索结果只作案例参考；提取候选需带 `case_id/root_id` lineage。
4. **`qd_agent_weights`**：建立完整 read/write consumer 清单，按层标记唯一生产者与消费者。对已被 `skill_events.weight_of()` 取代的 `layer='skill'` 旧读侧不得重新接回；`domain/tool/chain/factor/calibration` 各层需分别确定是否迁移、只读兼容或停用。不能用一条通用 win_rate 更新所有层。
5. **`qd_skill_selection_events/qd_skill_feedback`**：保留 selection funnel、冻结 skill version 和不可归因排除语义；通过 trace/decision 对照迁入 unified exposure 后，再切换新读侧。多 skill 协作不强行分配收益。
6. **Tool trace/weight feedback**：工具结果质量、数据新鲜度、延迟/成本和下游增量进入 typed evidence；旧工具权重在语义完成对照前只作为提示或禁用，不允许当成股票收益概率修正。
7. **冗余写链**：每个旧 writer 设置明确的 `read_only_since`、`disabled_since`、兼容结束版本和回滚策略；没有这些时间点不得宣布迁移完成。

### 24.8 代码落点与新增入口

首轮实现避免分散到 `qd_service.py`、`qd_aftercare.py` 或金融业务工具中。建议建立 `backend_api_python/app/agent/learning/`，提供以下边界：

- `contracts.py`：决策、经验、exposure、outcome、manifest 与状态的类型/校验；
- `store.py`：关系库唯一写入/读取薄层，事务、幂等和诊断；不在请求热路径建表；
- `experience.py`：候选验证、版本生命周期、检索和 condition DSL；
- `fusion.py`：单一决策输入组装、来源去重、受控融合和冲突状态；首期默认 `shadow`；
- `evaluation.py`：评估 manifest 调度、任务 evaluator 分派和报告落库；
- `evaluators/`：`stock_claims.py`、`market_selection.py`、`sector_selection.py`，板块内两阶段归因复用排序 evaluator；
- `migrations/`：版本化 SQL 与显式 migration apply/check 命令，不依赖 Flask 请求首次触发 DDL。

接线顺序：`qd_aftercare._finish_collector` 先保存 run/trace；完成现有 accountability 后把返回的 legacy decision/claim refs 与同一快照注册到 learning decision；记录当轮工具/技能候选与实际曝光；统一检索和融合先以 shadow 方式读取；T+N worker/CLI 按 manifest 计算 outcome。主对话与评估作业进程隔离，长回测不得同步阻塞 Agent 回复。

首期不新增生产交易 HTTP endpoint。提供受权限保护的 CLI/管理任务用于 `audit`、`import-legacy`、`evaluate`、`report`、`shadow-diff`、`publish`；publish 仅接受已验证 report ID 和 policy version。若未来提供 API，先只读查看决策证据卡与评估报告，禁止任意客户端直接写活跃系数。

### 24.10 必备测试矩阵与运维观察项

单元/集成 fixture 至少覆盖：

- 同一 run 多 subject、多 claim、多 horizon；claim 保存失败的 `None` 位不可错位；每 claim evidence 不能串用；

- DSL 结构/类型/单位/缺失值、未注册特征、超限交互、任意代码注入字符串；
- 同义标签校验：bullish、bearish、neutral、range、magnitude、level、ranking；禁止用 `verdict_score` 代替不匹配的概率标签；
- T+1 已成熟而 T+3/T+5 未成熟；假日、停牌、涨跌停不可成交、退市和价格源迟到；

- 旧 JSONL/DB 对账、claim/resolution 重试只取指定版本、历史 decision 按旧发布快照重放。
