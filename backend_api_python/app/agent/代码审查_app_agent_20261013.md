## 二、五大系统性问题(横向主题)

### ① 跨层字段契约靠「约定」不靠「结构」— 最危险
A 组 7 条全是同一病根:取数层与消费层之间传裸 dict/平行列表,缺列、键名不符、单位漂移、下标错位全部**静默**。修复必须是结构性的:SQL SELECT 列与消费字段同源定义、`[{id, claim}]` 成对返回消灭 zip、Returns 契约抽 TypedDict+契约测试。**禁止**在消费端补默认值盖住缺口(那正是漂移长期不被发现的原因)。

### ② 同功能重复实现 — 最大的维护债(见总账)
「统一出口」类承诺有三处名实不符:LLM 出口(llm.resolve_provider vs qd_service._build_default_model,两套优先级可能指向**不同模型**)、cron 解析(cron_worker vs cron/guards,已行为漂移:guard 放行的 `5/10` 在 worker 里 ValueError 静默停摆)、trace 三层(utils/tracing 死 + trace_collector + trace_adapter 双写)。每次"统一"之后都留了一个还在跑的旧通道。

### ③ 并发 / 超时 / 生命周期 — 最大系统性风险
「手工 Future 无 RUNNING 态 + to_thread 不可取消 + 钩子表按 session 而非 run 注册」三者叠加,停止/超时语义在 CLI/Web/Cron/直调四个入口各写一套且互相打架(C1/C2/C3 + M 级:M2 开跑即清停止位吞掉预约停止、M19 同 session 并发互删钩子)。另有全局态串台:redirect_stdout/sys.argv(strategy_debug)、dashscope.api_key(embeddings)、RedisMemory rpush/ltrim/expire 非原子可留无 TTL key、logger handler 竞态。建议任务生命周期收敛为 message_queue 内 Task 对象(state/stop-generation/timeout/钩子绑定同生命周期)。

### ④ 静默降级变「编造数据」— 与 grounding 红线冲突
fail-open(不阻断主链)是对的,但多处越过"降级"进入"编造":`agent_get_kline` 复权转换失败回退 qfq 数据但**谎报**请求口径(data_tools:231)、交易日历挂了按 `n*1.4` 自然日**猜**日期(resolvers/time:91,节假日误差一周)、东财封装异常返回 `[]` 与"没数据"不可辨(_em_utils)、板块名缓存一次瞬时失败=永久空映射(sector_analysis:322)、dragon 日期倒挂恒空不报错、success 空答案不落库(B6)。凡是降级后**产出看起来像真数据**的路径,都应改成显式缺失标注。

### ⑤ 死代码与假防御在积累
约 1500+ 行"看起来在工作"的代码(清单见第四节)。特别点名**假防御**:3 处 `try: from X import Y / except ImportError: from X import Y`(两支一字不差,resolvers/bridge、_fn_adapter、tool_discovery、qd_grounding)——出错时掩盖真实排障信息。死代码+好注释=更强的误导。
